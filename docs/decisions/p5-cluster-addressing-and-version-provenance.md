# P5 Cluster Addressing and Version Provenance

Date: 2026-08-18
Redis compatibility pin: Redis 7.2.5

## Scope

This record fixes two P5-milestone decisions that the `todo.md` closeout plan builds on: where PeaDB's own version number comes from, and what PeaDB's Redis Cluster surface is and is not going to be. Both were previously implicit or wrong in the codebase (`INFO` hardcoded a stale `peadb_version`, and `CLUSTER SLOTS`/redirects hardcoded `127.0.0.1`), so later tasks in the plan implement against this document rather than re-deriving the design each time.

## Version provenance

`VERSION` (a plain `MAJOR.MINOR.PATCH` file at the repo root) is the single source of truth for PeaDB's own version. The mechanism that carries it into the binary is a compile definition, `PEADB_VERSION`, not a generated header. This is a deliberate departure from the generated-header approach `todo.md` item 1 originally sketched (`include/peadb_version.hpp.in` plus a CMake `configure_file()` into `${CMAKE_CURRENT_BINARY_DIR}/generated/`).

The reason is concrete, not stylistic: `scripts/qa/run_fuzz_sanity.sh` compiles `src/command.cpp` by hand outside CMake, with an include path of only `-Iinclude` (`scripts/qa/run_fuzz_sanity.sh:89`, the `COMMON_FLAGS` line). That script is the fuzz sanity stage of `scripts/run_all_tests.sh` (stage 5 of the 9 listed in that script's own header comment as of this writing), which is unconditionally part of the mandatory pre-commit test suite. A header written into a CMake build directory is only visible to targets whose include path CMake itself wires up; the hand-rolled fuzz build never gets that path, so it would keep including whatever stale copy of the header last existed under `include/`, or fail to find it at all. A compile definition has no such problem: it is a command-line flag, so both the CMake build (`target_compile_definitions(peadb_core PUBLIC PEADB_VERSION="${PROJECT_VERSION}")`) and the fuzz script's hand-rolled `g++`/`clang++` invocation (`-DPEADB_VERSION="$(cat VERSION)"`) can supply it by reading the same `VERSION` file, with no generated artifact for either build path to fall out of sync with.

`include/peadb_version.hpp` contains an `#error` and no fallback value, on purpose: `#ifndef PEADB_VERSION` / `#error "PEADB_VERSION is not defined ..."`. A build configuration that forgets to define `PEADB_VERSION` must fail to compile, not silently compile a `0.1.0` (or worse, an empty string) into `INFO`. The customers this product serves run fleets of these binaries and file bug reports against `INFO`'s `peadb_version` field; a build that ships a wrong version silently is a build that misleads every downstream diagnosis of the bug it's reported against. A hard compile failure is loud, cheap to fix at build time, and impossible to ship by accident. Full implementation detail (the guard header text, the `CMakeLists.txt` wiring, the `src/main.cpp` startup log line) is `todo.md` item 1 / plan Task 1's job, not this record's; this record fixes only the mechanism and the reason for it.

`redis_version:7.2.5` stays hardcoded, at four sites: `src/command.cpp:3600` (the `INFO server` section), `src/command.cpp:1932` (`hello_reply`, the `HELLO` command's `version` field), `src/rdb.cpp:668` (the `redis-ver` RDB AUX field), and `src/lua_engine.cpp:1099` and `:1254` (the `redis.REDIS_VERSION` Lua global exposed to `EVAL` scripts and `FUNCTION`-loaded libraries). This is the Redis compatibility target fixed in `docs/decisions/d0-decisions.md` (D0.1), not PeaDB's own release number, and it must never move with PeaDB's release cadence. Tooling on the other side of the wire — `redis-cli`'s feature probes, client-library server-version gating, RDB loaders deciding which opcode set to expect — keys off this exact string to decide what protocol dialect and RDB layout to speak. Reporting PeaDB's own version there instead would break that tooling in a way that has nothing to do with an actual compatibility regression.

## Cluster addressing model

PeaDB's client-facing Cluster protocol targets Redis 7.2.5 faithfully: `CLUSTER SLOTS`/`SHARDS`/`NODES`/`INFO` reply shapes, `MOVED`/`ASK` redirects that name the real owning node's advertised address, and the `cluster-announce-ip`/`cluster-announce-port`/`cluster-announce-bus-port` config option names, matching Redis's own (`config.c:3105,3171-3172`). The port and bus-port defaults match Redis exactly: unset falls back to the client-facing port, and an unset bus port falls back to announced-port-plus-10000 (`config.c:3171-3172`, comments "Use server.port" / "Default: Use +10000 offset"). The IP default is a deliberate simplification, not a byte-for-byte mirror: Redis leaves the announced IP unset to force runtime auto-detection of the outbound-facing address per peer connection (`cluster.c:898-916`, `clusterUpdateMyselfIp`), while PeaDB falls back to the statically configured `bind` address instead. Auto-detecting a real outbound IP is unreliable behind NAT and inside containers, exactly the environments PeaDB's operator-configured model targets, so a static, operator-supplied fallback is more predictable than a per-connection guess. That static fallback carries a real hazard: a node bound to a wildcard address — `0.0.0.0`, which is the shipped `Dockerfile:39` default — would announce an address no peer can dial back. The compensating control is settled, not optional: with `cluster-enabled yes`, PeaDB refuses to start when the resolved announced host is a wildcard (`0.0.0.0`, `::`, `*`, or empty), failing with an error that names the option — this check applies to the resolved host unconditionally, not only when it was reached via the `bind` fallback, so an operator who sets `--cluster-announce-ip 0.0.0.0` explicitly is refused exactly as a wildcard-bind fallback would be (an earlier version of this guard gated on "no explicit `cluster-announce-ip` given," which let an explicit wildcard value through — closed in the same milestone). `CONFIG SET cluster-announce-ip` carries the same refusal at runtime, so the wildcard hazard cannot be reintroduced after startup either. A client speaking the Cluster protocol to a PeaDB node should not be able to tell, from the wire shapes alone, that there is no gossip protocol behind them.

What is **not** built, stated as plainly as what is: there is no cluster bus gossip protocol (the bus port opened at `announced_port + 10000` is a placeholder listener that answers a bare `PONG`, not a MEET/PING/PONG/FAIL message exchange — tracked as `compat/delta.md` item 6); no failure detection (no `PFAIL`/`FAIL` state machine, because there is no gossip channel for nodes to disagree about liveness over); no automatic failover (there are no replicas in the cluster model at all — see below — so there is nothing to promote); and no `nodes.conf` persistence (cluster topology is entered per node, via `CLUSTER MEET`/`SETSLOT`/`ADDSLOTS`/`ADDSLOTSRANGE`, and is lost on restart; an operator or their orchestration tooling must re-issue it, or script it into node startup, every time a node restarts).

The control plane is **operator-configured, not gossiped**. This trade is acceptable because of who runs PeaDB and how: the customers here are large, regulated organizations that already run a real orchestrator (Kubernetes, or an equivalent fleet manager) in front of every stateful service, and that orchestrator already owns membership and placement decisions for the pods it schedules. A from-scratch gossip protocol, failure detector, and automatic-failover state machine is a large, correctness-critical subsystem in its own right — exactly the kind of distributed-systems component that is easy to get subtly wrong and hard to prove correct, which this project's own standing rule (spend more development time rather than compromise correctness) argues against building speculatively. A fixed, externally-managed topology that changes only when an operator (or their automation) issues `CLUSTER MEET`/`SETSLOT` again is a smaller, auditable surface: every topology change is an explicit administrative action with a paper trail, not an emergent outcome of a gossip round nobody directly initiated. There are no replicas in the cluster model: each PeaDB node is a singleton with respect to slot ownership — `CLUSTER SETSLOT <slot> NODE <id>` assigns a slot to exactly one node, never a master-plus-replica pair, and `CLUSTER NODES` never emits a `slave` role line. PeaDB's separate `REPLICAOF` replication feature is unrelated to the cluster slot map; a deployment that wants both high availability and horizontal sharding must run its own replica-promotion logic on top of `REPLICAOF`, outside the cluster model, at least until a later milestone integrates them.

`cluster-enabled` becomes a startup-only option — set via config file or CLI flag, readable through `CONFIG GET`, and refused by `CONFIG SET` — for the same reason Redis treats it this way. Redis marks it `IMMUTABLE_CONFIG` (`config.c:3085`) and gates the entire `CLUSTER` command on it at the very top of `clusterCommand()`, before any subcommand dispatch: `if (server.cluster_enabled == 0) { addReplyError(c,"This instance has cluster support disabled"); return; }` (`cluster.c:5887-5891`). A `CONFIG SET` attempt against an `IMMUTABLE_CONFIG` parameter in Redis fails with `"CONFIG SET failed (possibly related to argument '%s') - can't set immutable config"` (`config.c:859,950`). PeaDB previously had no equivalent guard: whether a node was "in cluster mode" was inferred implicitly, at every `CLUSTER` subcommand call, from whether `g_cluster_peers` was non-empty — so a single successful `CLUSTER MEET` could flip a serving node's redirect behavior (whether an unmapped-slot `GET` returns data or a `-MOVED` error) in the middle of live traffic, with no restart and no operator decision recorded anywhere. The pinned Redis 7.2.5 source does not allow this: `cluster-enabled` is read once at startup and never reconsidered for the life of the process. This decision closes that gap by making `cluster-enabled` a real, `CONFIG SET`-refusing config field, matching Redis's own immutability guarantee for the same parameter.

Node IDs are derived deterministically from the announced address — `sha1_hex("peadb-cluster-node:" + announced_host + ":" + announced_port)` — rather than generated randomly and persisted to disk the way Redis does. Redis mints each node's 40-hex ID once, randomly, at first boot, and keeps it stable across restarts by writing it to `nodes.conf`. PeaDB has no `nodes.conf` and, per the operator-configured model above, no persisted cluster state of any kind; a randomly generated ID would rotate on every restart, which every other node in the cluster would have no way to distinguish from a genuine node replacement, breaking every `SETSLOT NODE <id>` reference to it. Deriving the ID from the announced address instead makes it stable across restarts for free, with no file to write, no file to lose, and no startup-ordering hazard between "generate an ID" and "load the persisted one." This is an acceptable trade specifically because the operator-configured model already requires a node's announced address to be a stable, operator-assigned fact — the same `cluster-announce-ip`/`-port` values are how peers already refer to this node in `SETSLOT NODE <host:port>` and in `MEET`. The costs are real and worth naming rather than glossing over: first, a node's ID is not stable across a genuine address change — re-announcing on a new IP or port mints a new ID, and every peer's slot-ownership table must be told about the new one explicitly, where Redis's persisted-random ID would have survived the address change unchanged; second, the ID is derivable by anyone who already knows (or can guess) the node's announced address, which is not a meaningful new disclosure since `CLUSTER NODES` already reveals every node's address in cleartext, but is worth recording as a departure from an opaque random identifier; third, two independently configured nodes that are accidentally given the same announced `host:port` collide on the same ID, where Redis's random generation would not — this is treated as an operator configuration error to be caught by deployment tooling, not something PeaDB's node-table code detects or refuses today.

## ACL model

PeaDB implements one implicit user, `default`; there is no user table and no rule engine. `requirepass` is that user's password (empty means `nopass`, matching Redis's own `ACLUpdateDefaultUserPassword` behavior). Read-only ACL introspection (`WHOAMI`, `USERS`, `LIST`, `CAT`, `GETUSER`, `GENPASS`, `HELP`) answers truthfully about this one-user reality — it never fabricates a multi-user picture. Every subcommand that would create or change a rule (`SETUSER`, `DELUSER`, `LOAD`, `SAVE`, `DRYRUN`) refuses with an explicit error naming the gap in `compat/delta.md` (items 1 and 7), rather than returning `+OK` for a rule it silently discards — this replaces the previous behavior where `ACL SETUSER` answered `+OK` while doing nothing.

`ACL LOG` refuses in the same way, rather than returning an empty array. Superficially, an empty array looks like the more Redis-faithful answer to "give me the ACL log" on a server that has logged nothing yet. But PeaDB does not merely have an empty log — it has no auth-failure recording mechanism behind `ACL LOG` at all, and never will until a real rule engine exists to generate log entries against. An empty-array reply is indistinguishable, on the wire, from "no failures have occurred," and an operator's or auditing tool's compliance checks routinely read exactly that signal — "zero ACL LOG entries" — as evidence that authentication is being enforced and nothing has failed. Returning an empty array here would let that auditing tool draw a false conclusion from an engine that was never watching in the first place. An explicit refusal cannot be misread that way: it tells the caller, unambiguously, that this data does not exist here, forcing them to look elsewhere (PeaDB's connection-level `-NOAUTH`/`-WRONGPASS` errors, application logs, or a future real ACL implementation) for authentication audit evidence instead of trusting a silently-empty log.
