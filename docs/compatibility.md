# PeaDB Compatibility & Migration

PeaDB targets **Redis 7.2.5** (commit `f60370ce28b946c1146dcea77c9c399d39601aaa`); behavior, error messages, and edge cases are validated against that exact version. [`../compat/delta.md`](../compat/delta.md) is the **canonical, always-current registry** of known gaps — this guide is a high-level orientation, not a substitute for it.

## Is it a drop-in replacement?

Not yet for data you cannot afford to lose. PeaDB speaks RESP2 (and basic RESP3) on port `6379`, and standard clients work unmodified for core workloads — strings, hashes, lists, sets, sorted sets, streams, transactions, Lua scripting, and pub/sub. Explicitly tested clients: `redis-py` 5.0.1, `node-redis` 4.6.13, `go-redis/v9` 9.5.1. `redis-cli`, `redis-benchmark`, `memtier_benchmark`, Jedis, and Lettuce also work.

But a verified review in 2026-10 found open defects that can lose or change data with no error: in RDB and AOF persistence, in replication, and on every migration path to and from Redis. They are [`compat/delta.md`](../compat/delta.md) items 24–79, and many are not fixed yet (each item says whether it is). Read them before you put data you need on PeaDB.

## Configuration

PeaDB loads its config file and command line the way `redis-server` 7.2.5 does: the same line splitting, setting names, aliases, value checks and error text, `include`, and `--name value` options parsed as config lines after the file. Where Redis's config loader refuses to start (a missing config file, an unknown name, the wrong number of arguments, a bad value or a bad `rename-command`), PeaDB refuses with the same reason and line. It also refuses the Redis settings it cannot honour safely, such as `user`, `aclfile`, `loadmodule` and settings that turn TLS on, so a hardened redis.conf can no longer start PeaDB with no password or without TLS by mistake; like any setting, these are judged on their final value. Every other Redis setting that PeaDB does not apply yet is accepted with one warning for each in the log ([`compat/delta.md`](../compat/delta.md) item 24 lists them and the few Redis checks PeaDB does not make). The settings PeaDB applies are listed in the [README Configuration section](../README.md#configuration). Like Redis, PeaDB makes `dir` its working directory. `CONFIG GET` and `CONFIG SET` follow Redis 7.2.5 too: `CONFIG GET` reports every Redis setting and alias (hidden ones only by exact name), and `CONFIG SET` takes several settings at once, all or nothing, with Redis's error for an unknown name, an immutable or protected setting (`dir` and `dbfilename` need `enable-protected-configs`), a repeated name and a bad value. The settings PeaDB applies take effect at once, including `appendonly yes` (which starts the AOF with a rewrite of the data, as in Redis), `maxclients`, `proto-max-bulk-len` and `client-query-buffer-limit`; `port` and `bind` cannot change while PeaDB runs yet (item 25). A Redis setting that PeaDB does not apply either has a fixed value that describes what PeaDB always does, which `CONFIG GET` reports and `CONFIG SET` keeps (any other value is refused, for example `rdbcompression yes`), or it keeps the value it is given, has no effect, and gets a warning in the log, as in the config file (item 24). So a `CONFIG SET` that answers `OK` for a setting PeaDB applies has applied it. Use `CONFIG REWRITE` to persist runtime settings and role changes to the startup config file; see [item 25](../compat/delta.md) for publication guarantees and include/default-user boundaries.

## Live migration & rollback

The supported migration and rollback paths are exercised by the [migration acceptance gate](../tests/acceptance/migration.py), which blocks release image publication. Its scope and remaining boundaries are recorded in [`compat/delta.md`](../compat/delta.md) item 49.

1. Start PeaDB beside the existing Redis master.
2. Run `REPLICAOF <redis-host> <redis-port>` — PeaDB performs a native in-process PSYNC2 full sync (RDB load, then a continuous command stream). Slow disk-backed saves and authentication to a named Redis ACL user work (item 50). Set `masterauth` to the master password; when its default user is disabled, also set `masteruser` to an enabled user allowed to run `PING`, `REPLCONF` and `PSYNC`. Both settings accept config/CLI and CONFIG SET; credential changes apply on the next handshake. An empty username uses password-only AUTH, and an empty password skips AUTH. Native Redis 7.2.5 stream and collection snapshots are supported (items 5 and 51); older zipmap/ziplist encodings also load natively; snapshots selecting a database outside 0–15 are refused (item 53).
3. Quiesce application writers, record the master’s `master_repl_offset` from `INFO replication`, and wait until the replica reports `master_link_status:up` and `slave_repl_offset` at least that offset. A connected link alone does not prove catch-up. Keep writers paused through promotion and client cutover; retain a backup of the original server.
4. Run `REPLICAOF NO ONE` on PeaDB and repoint application clients. The received snapshot and replicated AOF effects survive restart (item 45, fixed). With AOF enabled, wait for the full-sync replacement rewrite to finish successfully before relying on restart durability. Run `CONFIG REWRITE` after promotion (or remove the `replicaof` line manually) to retain the new role on restart; runtime REPLICAOF alone does not change the startup file (item 25). Replicas attached to the promoted server get every later write: Redis and PeaDB replicas resume cached history with a partial resync (item 47, fixed).

To **roll back**, quiesce writers again, then export a Redis-readable RDB with `SAVE`/`BGSAVE` and load it into Redis, or attach a Redis replica and promote it after catching up. Native stream snapshots and DUMP/RESTORE/MIGRATE are checked in both directions, including history, consumer groups and pending messages (items 5/51). The acceptance scope is in item 49; native loading of older encodings/database-range refusal is complete in item 53. For offline import and export, quiesce application writes and use the bridge scripts:

```bash
# Set PEADB_PASSWORD in the process environment if authentication is required.
python3 scripts/redis/import_rdb_via_redis.py --rdb /path/to/dump.rdb --peadb-port 6379
python3 scripts/redis/export_rdb_via_redis.py --peadb-port 6379 --out /path/to/output.rdb
```

For an offline native snapshot in either direction, quiesce writers and require `SAVE` to return `OK` before copying `dir`/`dbfilename`. Keep the original backup, copy the file into a fresh target data directory under its configured `dbfilename`, and start the target with `appendonly no`, authentication and enough databases for the snapshot (PeaDB supports 0–15). An authenticated `PING` must succeed after loading; compare all database contents, absolute expiries, stream metadata and functions before switching clients. Starting with `appendonly yes` and only an RDB does not load that RDB: enable AOF on the loaded server instead if required, using the [persistence procedure](#persistence--durability). The acceptance gate exercises both native snapshot directions with fresh target directories.

The scripts use the pinned Redis 7.2.5 build (provision with `bash scripts/ci/ensure_redis_reference.sh`, or set `REDIS_SERVER` to its binary) in a private temporary directory with an ephemeral loopback port and random authentication secret. They copy every configured database, binary keys/values, exact 64-bit absolute expiry deadlines, stream history/groups/consumers/pending entries and function libraries through native DUMP/RESTORE and FUNCTION DUMP/RESTORE. The live endpoint authenticates using `PEADB_PASSWORD` or `--peadb-password`; prefer the environment to keep the password out of process arguments. Add `--peadb-user USER` for named Redis ACL authentication. The account needs PING, CONFIG GET databases, SELECT, SCAN, MULTI, EXEC, DUMP, PEXPIRETIME and FUNCTION DUMP for export; import needs PING, CONFIG GET databases, SELECT, RESTORE and FUNCTION RESTORE, plus FLUSHALL and FUNCTION FLUSH with `--flush-target`. Renamed/disabled commands or missing permissions are errors, not skipped data.

Import replaces each source key and same-named function library; unrelated target keys and libraries remain. Use `--flush-target` to clear **all target keys and functions** before copying, after authentication and source startup/database/function preflight succeed. The temporary source defaults to 16 databases; for an RDB from a differently configured Redis pass `--databases N`. A source configured with more databases than the target is refused before copying or flushing, even if the extra databases are empty. PeaDB currently has 16 databases. `--source-port` (import) and `--target-port` (export) optionally select a fixed temporary port; an occupied port fails. `--timeout SECONDS` sets the socket/startup budget (default 30).

Every reply is checked. Any authentication, ACL, protocol, loading, write, SAVE or publication failure exits nonzero without printing success or credential contents; exports replace `--out` atomically only after a successful SAVE. An import can be **partial** if a later operation fails; it has no rollback. A successful empty-source run reports zero key transfers explicitly, and SCAN duplicates can increase the transfer count. These scripts provide neither a live dataset snapshot nor a migration transaction: pause writers, verify per-database contents/functions and keep a backup before switching clients. Keys whose deadlines pass during transfer expire naturally without a TTL extension. Large keys require memory for their DUMP payload and its RESTORE request, and transfer is sequential; see the measured acceptance scope in item 49. See [`../compat/delta.md`](../compat/delta.md) item 52 for the completed regression coverage.

### Migration acceptance gate

After building Release and provisioning the pinned reference, run the same gate used by the release workflow (choose a new work directory):

```bash
python3 tests/acceptance/migration.py --work-dir artifacts/migration-local
```

Each source contains 2,000,100 generated keys, evenly mixing strings, lists, sets, hashes, sorted sets and streams across databases 0, 1 and 15, plus binary/empty names and values, exact absolute expiries (including a deadline above 2⁵³), stream history/deleted IDs/groups/PEL/empty consumers and two function libraries. The gate checks every generated value and expiry, exact native stream metadata, all database counts (including empty databases), library definitions and function execution. It records per-database logical SHA-256 digests, startup/full-sync durations, phase times and sampled RSS for direct child processes in `report.json` (temporary Redis grandchildren are outside that RSS sample). Native snapshot loading, replication with live writes/promotion/AOF restart, Redis RDB bridge import into PeaDB and PeaDB bridge export into Redis must all finish; failure exits nonzero and retains logs/data. Initial full sync checks metadata before live writes. Full-sync time includes native structural preflight and applying the snapshot; it does not isolate the cost of the second decode pass.

The default total budget is 5,400 seconds, with a 300-second startup/socket/full-sync limit and a 3,072 MiB address-space cap per child on Linux (including temporary Redis). Reserve at least 8 GiB RAM and 4 GiB scratch disk. macOS runs have the same execution bounds and record sampled server RSS, but do not enforce the Linux address-space cap. `--keys`, `--budget-seconds`, `--timeout` and `--memory-mib` adjust these bounds. Fewer than 2,000,001 generated keys is refused unless `--smoke` is explicit; smoke reports `smoke_passed`, never release acceptance. The normal integration suite runs only a small smoke; sanitizer smoke omits the virtual-address cap because ASAN reserves a large address range. Release publication runs the full gate on Ubuntu against Release binaries; this bounded representative dataset is not a proof for arbitrary Lua libraries, unavailable memory or concurrent writers.

**Command-based AOF rewrite has Redis’s stream metadata limits.** With `aof-use-rdb-preamble no` (PeaDB’s supported mode), replay recreates consumer activity timestamps and drops pending IDs whose messages were already deleted. The gate reproduces this on pinned Redis first, checks these precise semantics on both promoted servers after restart, and keeps value/expiry/history/group offsets/surviving PEL owner/time/delivery-count checks active. Snapshot, initial full sync and bridge comparisons require the original metadata unchanged. Keep a native RDB backup if the original activity timestamps or deleted-message pending records are required after restart. This procedure does not promise direct portability of Redis’s multipart AOF directory into PeaDB; use the native RDB/replication/bridge paths for transfer.

## Persistence & durability

RDB restarts can resume replication from saved history when the upstream still holds the requested bytes. AOF restarts and snapshots without usable metadata require full synchronization. Restart guarantees and fallback boundaries are documented in [delta item 47](../compat/delta.md).

Full sync uses a forked disk snapshot at `dir`/`dbfilename`, even with save points disabled, so the master needs a writable data directory and space for the snapshot. RDB bytes stream separately from the replica output buffer; post-fork command bytes retain the configured buffer limits. See [`../compat/delta.md`](../compat/delta.md) item 46 for behavior and remaining diskless/writer differences.

A replica and an AOF reload apply writes regardless of client limits or the local cluster slot map. Replication errors are logged and counted in `INFO stats` as `unexpected_error_replies`. With a local persistence error, a replica stops on the next write from its master unless `replica-ignore-disk-write-errors yes` is set; that setting keeps applying with a rate-limited warning, as Redis 7.2.5 does. See [`../compat/delta.md`](../compat/delta.md) item 43.

PeaDB offers Redis's durability options, but not yet Redis's durability. The single-server defects of the 2026-10 review that lost acknowledged writes or stopped the next restart are fixed ([`compat/delta.md`](../compat/delta.md) items 27–37), as are replica persistence and link liveness (items 45 and 47). Deterministic stream claim propagation and native RDB database-range handling are fixed (items 48/53). The bullets below describe the persistence behavior and remaining limits.

- **RDB snapshots** — `SAVE` (blocking) and `BGSAVE` (forked) write an RDB in Redis's format, with Redis's CRC64 checksum, to `--dir`/`--dbfilename`, and PeaDB loads the RDB files real Redis 7.2.5 writes (item 27 is fixed). Lists of any length are saved in nodes the way Redis splits them by `list-max-listpack-size` (item 29, fixed), and `SAVE` is refused while a `BGSAVE` runs. As in Redis, a save writes expired keys too, with their expire time, and a master that loads the file leaves them out (before 2026-10-07 a save deleted them without sending their `DEL` to the replicas, item 37). A `BGSAVE` that fails, including a failed `fork()`, is logged with Redis's lines and sets `rdb_last_bgsave_status:err`, so with save points writes are refused with `-MISCONF` until a save succeeds; `rdb_last_save_time`, `LASTSAVE` and `rdb_changes_since_last_save` move only after a good save; `FLUSHALL` stops a running `BGSAVE` and, with save points, saves the empty dataset at once; a `BGSAVE` inside `MULTI`/`EXEC` runs after `EXEC`, and one during an AOF rewrite is refused or, with `BGSAVE SCHEDULE`, run after it (item 34, fixed 2026-10-06), and a `BGREWRITEAOF` during a `BGSAVE` runs after it (item 3, fixed 2026-10-07). Files with older zipmap/ziplist encodings load natively; database-range checks and the full-sync validation boundary are documented in item 53. The writer fsyncs the file and its parent directory and fails the save on any fsync error rather than leaving a corrupt snapshot. Every load checks the trailing **CRC64**, as Redis does (PeaDB checks it before it replaces the data in memory, Redis after reading the keys): on startup a corrupt native RDB (`REDIS` magic, bad checksum) is fatal — the server refuses to start rather than silently falling back to an empty/legacy load — and a replica whose full-sync RDB fails the check keeps its data and retries the sync. As in Redis, `rdbchecksum no` (startup only) skips the check and saves a zero checksum, and a file with a zero checksum loads without a check. A file cut short is refused even then. This is also how to load a `dump.rdb` written by PeaDB before 2026-10-06, whose checksum used the wrong table: start PeaDB once with `--rdbchecksum no`, run `SAVE`, and restart without it. An AOF written by that older PeaDB that holds `RESTORE` or `FUNCTION RESTORE` lines stops startup; run `BGREWRITEAOF` on the older PeaDB before upgrading.
- **AOF** — enable with `--appendonly yes`; commands append to a persistent fd. The `appendfsync` policy governs durability:

  | `appendfsync` | Behavior | Worst-case loss on crash |
  |---------------|----------|--------------------------|
  | `always` | fsync after every write | none for acknowledged writes: a failed write or fsync stops the server (exit code 1) before the client gets its reply, as in Redis (item 35, fixed), and a transaction or script is written whole or not at all (item 36, fixed); on macOS PeaDB's `fsync()` does not flush the disk's own cache as Redis's `F_FULLFSYNC` does |
  | `everysec` *(default)* | fsync ~once per second | ~1 second of writes |
  | `no` | flushing left to the OS | OS-buffer dependent |

  `BGREWRITEAOF` forks a child to rewrite, then the parent atomically renames the result over the live file. A failed AOF write or `everysec` fsync is handled like Redis's `flushAppendOnlyFile()`: the bytes that did not reach the file stay in memory (a short write is cut off the file again), `INFO` shows `aof_last_write_status:err`, writes and `PING` are refused with `-MISCONF Errors writing to the AOF file: <reason>`, and the bytes are written again on each event-loop pass, so once the disk works again the error clears by itself and no acknowledged write is lost (before 2026-10-07 the bytes were dropped and the server stayed read-only until a restart, item 35). Unlike Redis, a shutdown refuses to exit while those bytes cannot be written (`SHUTDOWN FORCE` exits anyway), and a failing fsync is tried again every second. On startup a **truncated AOF tail** (a crash in the middle of the last write) is cut off the file at the last whole command and logged, as Redis does with `aof-load-truncated yes` (the default), so later writes follow good data and the next restart loads them (before 2026-10-06 the file was not cut and the next restart failed, item 30); with `aof-load-truncated no` the server refuses to start instead. **Bytes that are not a command are fatal** wherever they are — the server refuses to start rather than serve partial data. As in Redis, a transaction, a script or a function that writes more than once is written to the AOF, and sent to the replicas, wrapped in `MULTI`/`EXEC` in one write, and the loader drops a `MULTI` whose `EXEC` is missing, so a crash never replays half of it (before 2026-10-07 each write was written alone, item 36). As in Redis, the `DEL` of every key that expires reaches the AOF and the replicas (inside the transaction of the command that met it), and no key expires while the AOF loads, so an AOF written while a key was alive no longer brings it back as a new key without a TTL after the TTL has passed (before 2026-10-07 the loader deleted the expired key before the next write to it, so `SET k 5 PX 400` then `INCR k` came back as `k` = `1`; item 37). An evicted key's `DEL` is written after a `SELECT` of its database (before, a restart could delete a key of the same name in another database and bring the evicted key back). `BGREWRITEAOF` and `CONFIG SET appendonly yes` during a `BGSAVE` or inside `MULTI`/`EXEC` start the rewrite after it, as in Redis (item 3). The AOF loads whatever `maxmemory` and `min-replicas-to-write` say, as in Redis (before, startup stopped once the replayed data went over `maxmemory`, item 43). With the AOF on, startup loads only the AOF, as Redis does, so a `dump.rdb` in `--dir` is not loaded as well (before 2026-10-06 it was, and every write was applied twice, item 28). This is also true when the AOF is empty or new: turning on `appendonly yes` in the config of a server that has only a `dump.rdb` starts it with no data (PeaDB logs a warning naming the file). To move an RDB dataset to the AOF, start with the AOF off and run `CONFIG SET appendonly yes`, which writes the data into the AOF. An AOF that cannot be opened stops startup, as in Redis.
- **Save points** — `save <seconds> <changes>` (config or `CONFIG SET save`, repeatable; `save ""` disables) trigger a background `BGSAVE` when enough keys changed within the window, and `SHUTDOWN [SAVE|NOSAVE]` saves on a clean shutdown when save points are configured. SIGTERM (what `systemctl stop`, `docker stop` and Kubernetes send) and SIGINT shut down the same way, with the flags of `shutdown-on-sigterm`/`shutdown-on-sigint`, and a second SIGINT exits at once without saving; SIGHUP is ignored, as in Redis. A shutdown first stops a running `BGSAVE` child. `SHUTDOWN` answers and logs like Redis's, including `SHUTDOWN ABORT`, a failed save that keeps the server running, and `FORCE`. As in Redis, a master whose replicas have not acknowledged every write waits for them before it exits, for at most `shutdown-timeout` seconds (default 10; `SHUTDOWN NOW` and `shutdown-timeout 0` do not wait): it asks them for an acknowledgement, holds writes but keeps serving reads, shows `shutdown_in_milliseconds` in `INFO`, keeps the `SHUTDOWN` client waiting and logs each replica that is still behind; `SHUTDOWN ABORT` cancels the wait (item 33, fixed 2026-10-09). A replica acknowledges what it has applied (item 44, fixed 2026-10-09), so the wait ends once every replica has applied every write. The default ships **no** save points (set them, or enable AOF, to persist) — so an out-of-the-box instance with neither is non-durable, exactly like Redis started with `save ""` and `appendonly no`.
- **Streams** — persist via both **RDB** (entries + consumer groups + full PEL, native Redis v11 encoding) and AOF, and replicate through PSYNC. Claim options follow Redis 7.2.5; absolute delivery times, retry counts, owners and group cursors are preserved through claim replication and AOF restart/rewrite (delta item 48). Redis history reads intentionally update local PEL time/count without propagation. As in Redis, canonical stream commands written to AOF must be available at startup: restore their original names before loading an AOF when XCLAIM was renamed or disabled. Native stream snapshots and DUMP/RESTORE/MIGRATE work with real Redis; see delta items 5/51.

## Operational notes

- **Security** — default-user authentication is enforced: set `requirepass` (config/CLI/`CONFIG SET`) and unauthenticated clients get `-NOAUTH` for every non-`no_auth` command; `AUTH` / `HELLO … AUTH` validate with a compare whose time does not depend on the password's content, though it can reveal the password's length (item 61). Only `requirepass` sets a password: a config with `user` or `aclfile` lines refuses to start, because there are no ACL users (item 24). **protected-mode** is on by default, so a server with no password refuses non-loopback clients. `MODULE LOAD` (which runs arbitrary native code) is gated behind `enable-module-command` (default off), `rename-command` can neutralise dangerous verbs, and `proto-max-bulk-len`/multibulk + query-buffer caps bound a malicious client's memory. `DEBUG` is open to every authenticated client, where Redis 7.2.5 needs `enable-debug-command` (item 61). To disable it, put `rename-command DEBUG ""` in the config file, as in Redis; `enable-debug-command no` stops startup instead, because PeaDB cannot apply it yet (item 24). `ACL WHOAMI`/`USERS`/`LIST`/`CAT`/`GETUSER`/`GENPASS`/`HELP` truthfully report the single `default` user (password shown as `#<sha256-hex>` of `requirepass`, or `nopass`); `ACL SETUSER`/`DELUSER`/`LOAD`/`SAVE`/`LOG`/`DRYRUN` refuse with an error naming the gap rather than applying, discarding, or faking a rule. **Still missing:** a multi-user **ACL** rule engine and **TLS** — terminate TLS at a proxy and keep multi-tenant isolation at the network layer until both land.
- **Memory pressure & eviction** — `maxmemory` sets a byte limit (with `100mb`/`2gb` unit parsing in both config and `CONFIG SET`). `used_memory` is what Redis's is: a count of every byte the process holds on the heap (PeaDB replaces the global `operator new`/`operator delete` to keep it, as Redis's `zmalloc` does), so it includes container and allocator overhead and client buffers, and reading it costs nothing; the limit is checked against it less the replicas' output buffers and the AOF buffer (INFO `mem_not_counted_for_evict`), as Redis does, so a slow replica cannot make the server evict keys (item 38). PeaDB's values take more memory than Redis's for the same data (item 13), so the same `maxmemory` holds fewer keys. When used memory exceeds the limit, PeaDB **evicts** keys per `maxmemory-policy` — all eight Redis modes: `noeviction` (default), `allkeys-lru`/`-lfu`/`-random`, and `volatile-lru`/`-lfu`/`-random`/`-ttl` — before each command a client sends, in steps of `maxmemory-eviction-tenacity` (default 500 µs) with the rest done in the background, as Redis's `performEvictions()` does, so a large eviction (for example after lowering `maxmemory` with `CONFIG SET`) never stops the server for long. Eviction uses approximate sampling (`maxmemory-samples`, default 5) over a random bucket walk across all DBs (or only TTL-bearing keys for `volatile-*`), without Redis's eviction pool, and LFU counters never decay (item 12); the chosen victim is evicted, counted in `evicted_keys`, propagated as a `DEL` to replicas and the AOF, and emits an `evicted` keyspace notification. With `noeviction` (or when a `volatile-*` policy has no eligible keys) only commands that can grow memory (Redis's `denyoom` flag: `SET`, `RPUSH`, `SADD`, …, and scripts and functions that declare flags without `allow-oom` or `no-writes`) are refused with `-OOM command not allowed when used memory > 'maxmemory'.`, so `DEL`, `UNLINK`, `EXPIRE`, pops and reads still clean up a full server; inside `MULTI` every command is refused while memory is over, and a script is never stopped half done (item 39). LRU/LFU metadata is approximate (a coarse access clock / log-increment counter touched on the command's primary key). `stop-writes-on-bgsave-error` (default on) additionally rejects writes with `-MISCONF` when a background save has failed and save points are set (then `PING` too, as in Redis), or when an AOF write is failing.
- **Monitoring** — there is no HTTP `/metrics` endpoint, but the standard tooling works: `INFO` (community exporters such as `redis_exporter` scrape it) now reports real `blocked_clients`, `used_memory_rss`/`mem_fragmentation_ratio`, `used_memory_peak`, `used_cpu_*`, `latest_fork_usec`/`total_forks`, `instantaneous_ops_per_sec`, and `pubsub_channels`. About 15 standard fields are still missing (for example `run_id`, `rejected_connections` and the per-replica `slaveN:` lines), so some exporter alerts never fire and Redis Sentinel cannot manage PeaDB (item 22), and an INFO that includes the keyspace section (the default INFO does) walks the whole keyspace, so frequent scrapes of a large instance stall every client (item 55; `INFO memory` and the other sections no longer walk it). `SLOWLOG` is **populated** (real per-command timing via `slowlog-log-slower-than`/`slowlog-max-len`), `INFO commandstats` reports real `usec`/`usec_per_call`, `LATENCY LATEST`/`HISTORY`/`RESET`/`DOCTOR` work (gated by `latency-monitor-threshold`), `MONITOR` streams live commands, `CLIENT LIST`/`CLIENT KILL` (with Redis 7.2's `ID`, `TYPE`, `ADDR`, `LADDR`, `USER` and `SKIPME` filters) and runtime `CONFIG SET loglevel` work. **Keyspace notifications** (`notify-keyspace-events`, `__keyspace@`/`__keyevent@`, incl. `expired`) are implemented, but many write commands send no event or the wrong one: for example a pop that empties a key sends no `del`, and LMOVE, SMOVE and the store commands send nothing (item 72).
- **Connections** — accepted client sockets get `TCP_NODELAY` and, unless `tcp-keepalive` is `0`, TCP keepalive probes after `tcp-keepalive` seconds of silence (Redis's default 300), so half-open peers are detected and reaped. An idle-client `timeout` (seconds; config/CLI/`CONFIG SET`, default 0 = off) closes clients idle past the window; replicas, blocked/`WAIT`ing/`MULTI` clients and pub/sub subscribers are exempt. `client-output-buffer-limit` is enforced per class (`normal`/`slave`/`pubsub`) with Redis-default hard/soft/soft-seconds (normal unlimited; replica 256mb/64mb/60; pubsub 32mb/8mb/60): a slow consumer or lagging replica whose buffer exceeds its limit is disconnected instead of OOMing the single process.
- **Cluster configuration** — cluster mode is **experimental and not production-safe** ([`compat/delta.md`](../compat/delta.md) items 6 and 64–67). `cluster-enabled` (config/CLI, default `no`) is startup-only, like Redis's own `IMMUTABLE_CONFIG` treatment of the same parameter; `CONFIG SET cluster-enabled` is refused. `cluster-announce-ip`/`-port`/`-bus-port` (config/CLI/`CONFIG SET`) name the address/ports this node advertises to peers and clients; an unset announce-ip falls back to `bind`, a documented simplification of Redis's live-connection auto-detection (see [`docs/decisions/p5-cluster-addressing-and-version-provenance.md`](decisions/p5-cluster-addressing-and-version-provenance.md) for the full rationale). Because that fallback would otherwise announce an unreachable wildcard address, a node started with `cluster-enabled yes` **refuses to start** if the resolved announced host is `0.0.0.0`, `::`, `*`, or empty — whether that resolution comes from the `bind` fallback or from an explicit `cluster-announce-ip` naming a wildcard itself — set `cluster-announce-ip` to a real, peer-reachable address for any node bound to a wildcard address (including the shipped `Dockerfile`, which binds `0.0.0.0`). `CONFIG SET cluster-announce-ip` refuses the same wildcard values at runtime, matching the startup guard. `redis_mode` in `INFO` and the `cluster_enabled` field (in both `# Server` and `# Cluster`) all derive from the same `cluster-enabled` state, so they cannot disagree. The cluster bus listener (port + 10000) only opens when `cluster-enabled yes`.
- **TLS** — not supported; terminate TLS at a proxy (stunnel, Envoy, a cloud load balancer).
- **OS** — Linux is the primary target (kernel 5.15+ enables the optional io_uring backend); GCC 11+/Clang 14+ and CMake ≥ 3.16. Windows is a non-goal for production.
