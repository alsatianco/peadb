# PeaDB Compatibility & Migration

PeaDB targets **Redis 7.2.5** (commit `f60370ce28b946c1146dcea77c9c399d39601aaa`); behavior, error messages, and edge cases are validated against that exact version. [`../compat/delta.md`](../compat/delta.md) is the **canonical, always-current registry** of known gaps — this guide is a high-level orientation, not a substitute for it.

## Is it a drop-in replacement?

Not yet for data you cannot afford to lose. PeaDB speaks RESP2 (and basic RESP3) on port `6379`, and standard clients work unmodified for core workloads — strings, hashes, lists, sets, sorted sets, streams, transactions, Lua scripting, and pub/sub. Explicitly tested clients: `redis-py` 5.0.1, `node-redis` 4.6.13, `go-redis/v9` 9.5.1. `redis-cli`, `redis-benchmark`, `memtier_benchmark`, Jedis, and Lettuce also work.

But a verified review in 2026-10 found open defects that can lose or change data with no error: in RDB and AOF persistence, in replication, in `SCAN`, in list and sorted-set edits that remove a key's TTL, and on every migration path to and from Redis. They are [`compat/delta.md`](../compat/delta.md) items 24–71, and none is fixed yet. Read them before you put data you need on PeaDB.

## Configuration

PeaDB parses redis.conf-style files (`key value` lines, `#` comments) — either redis-server style (first positional argument) or `--config <path>`; CLI flags override file values. Recognized keys are a subset of Redis's (the full table lives in the [README Configuration section](../README.md#configuration)). Every other directive, and a missing config file, is accepted and ignored with no warning, where Redis refuses to start. This includes `user`, `aclfile`, `include` and `tls-*`: a hardened redis.conf that sets its password through `user` or an ACL file starts PeaDB with **no password**, and a TLS config gives a plaintext server ([`compat/delta.md`](../compat/delta.md) item 24). `CONFIG SET` changes are in-memory only; there is no `CONFIG REWRITE`, so runtime changes do not survive a restart. `CONFIG SET` is lenient too. A parameter name PeaDB does not recognize (a typo, or a real Redis parameter not yet implemented) returns `+OK` rather than Redis's `ERR Unknown option or number of arguments for CONFIG SET - '<param>'` (item 23; deliberately left as-is for now, because making it strict is a behavior change with its own rollout considerations). Some known parameters — `appendonly`, `dir`, `dbfilename`, `proto-max-bulk-len` and `maxclients` — return `OK` but change nothing, and `CONFIG GET dir` returns the process working directory rather than `--dir` (item 25). So `CONFIG SET`'s `OK` is not on its own proof that a change was applied.

## Live migration & rollback

**None of these paths works end to end today**; [`compat/delta.md`](../compat/delta.md) item 49 lists every defect, and it stays open until an acceptance test passes in both directions. The intended steps are below, each with the defect that breaks it now.

1. Start PeaDB beside the existing Redis master.
2. Run `REPLICAOF <redis-host> <redis-port>` — PeaDB performs a native in-process PSYNC2 full sync (RDB load, then a continuous command stream). Today this fails when the master needs more than about 1 s to produce its RDB, which is any real production dataset, and PeaDB cannot sync from a master whose default user is disabled, because it has no `masteruser` (item 50).
3. Wait until `INFO replication` shows the replica caught up.
4. Run `REPLICAOF NO ONE` on PeaDB and repoint application clients. Today a PeaDB replica does not write the data it received through replication to its own RDB or AOF, so after promotion its first restart loads only the writes made after the promotion (item 45).

To **roll back**, the plan is to export a Redis-readable RDB with `SAVE`/`BGSAVE` (or `scripts/redis/export_rdb_via_redis.py`) and load it into Redis. Today real Redis refuses every PeaDB RDB, because PeaDB's RDB checksum uses the wrong table; for the same reason a real Redis replica of a PeaDB master fails, and `DUMP`/`RESTORE`/`MIGRATE` fail across engines (items 27 and 51). For offline import and export, the bridge scripts are:

```bash
python3 scripts/redis/import_rdb_via_redis.py <dump.rdb>     # Redis RDB -> PeaDB
python3 scripts/redis/export_rdb_via_redis.py <output.rdb>   # PeaDB -> Redis RDB
```

The bridge scripts use a temporary Redis instance. They have no password option and do not check replies, so against a server with `requirepass` they copy nothing and still exit 0; they also copy only database 0 and skip consumer groups and functions (item 52). Check the key counts on both sides after every run. **Streams** persist and replicate within PeaDB (PSYNC full-sync handles stream datasets), but PeaDB's stream RDB encoding is PeaDB-specific — a real `redis-server` cannot load a PeaDB RDB that contains streams (item 5). No cross-engine stream path is complete: the bridge scripts drop consumer groups, and loading a PeaDB AOF into Redis has not been tested (item 49).

## Persistence & durability

PeaDB offers Redis's durability options, but not yet Redis's durability: open defects can lose acknowledged writes or stop the next restart ([`compat/delta.md`](../compat/delta.md) items 27–37, none fixed yet). The bullets below name the main ones.

- **RDB snapshots** — `SAVE` (blocking) and `BGSAVE` (forked) write an RDB in Redis's format to `--dir`/`--dbfilename`, but with a CRC64 checksum computed from the wrong table, so real Redis refuses PeaDB's files and PeaDB refuses real Redis's (item 27). Lists of 65,536 or more items are cut on save (item 29), and a foreground `SAVE` during a `BGSAVE` writes the same temp file (item 34). The writer fsyncs the file and its parent directory and fails the save on any fsync error rather than leaving a corrupt snapshot. On startup the trailing **CRC64 is verified** (with that same table): a corrupt native RDB (`REDIS` magic, bad checksum) is fatal — the server refuses to start rather than silently falling back to an empty/legacy load. (Replication-stream RDBs skip CRC, since a foreign master's CRC variant differs; that path is integrity-checked by TCP + length framing.)
- **AOF** — enable with `--appendonly yes`; commands append to a persistent fd. The `appendfsync` policy governs durability:

  | `appendfsync` | Behavior | Worst-case loss on crash |
  |---------------|----------|--------------------------|
  | `always` | fsync after every write | none while every write and fsync succeeds; today a failed write or fsync is still answered `OK`, where Redis exits (item 35) |
  | `everysec` *(default)* | fsync ~once per second | ~1 second of writes |
  | `no` | flushing left to the OS | OS-buffer dependent |

  `BGREWRITEAOF` forks a child to rewrite, then the parent atomically renames the result over the live file. `appendfsync always`/`everysec` check the `fsync()` return and flag a write error, after which writes are refused with `-MISCONF`; nothing clears that flag, so the server stays read-only until a restart (item 35). On startup a **truncated AOF tail** is tolerated (logged, `aof-load-truncated` default yes), but the file is not cut, so new writes land after the torn bytes and the next restart fails (item 30); **mid-file corruption is fatal** — the server refuses to start rather than serve partial data. Transactions and scripts are not wrapped in `MULTI`/`EXEC` in the AOF, so a crash can replay half a transaction (item 36). With both an AOF and a `dump.rdb` in `--dir`, startup loads the RDB and then replays the whole AOF on top, so writes are applied twice; Redis loads only the AOF (item 28).
- **Save points** — `save <seconds> <changes>` (config or `CONFIG SET save`, repeatable; `save ""` disables) trigger a background `BGSAVE` when enough keys changed within the window, and `SHUTDOWN [SAVE|NOSAVE]` saves on a clean shutdown when save points are configured. SIGTERM (what `systemctl stop`, `docker stop` and Kubernetes send) and SIGINT exit without that final save, and SIGHUP kills the server, so an RDB-only server loses every write since the last save point on each stop (item 33). The default ships **no** save points (set them, or enable AOF, to persist) — so an out-of-the-box instance with neither is non-durable, exactly like Redis started with `save ""` and `appendonly no`.
- **Streams** — persist via both **RDB** (entries + consumer groups + full PEL, PeaDB-internal encoding) and AOF, and replicate through PSYNC. A PeaDB RDB containing streams is not loadable by real Redis (PeaDB-specific stream type); use AOF/bridge for cross-engine stream migration.

## Operational notes

- **Security** — default-user authentication is enforced: set `requirepass` (config/CLI/`CONFIG SET`) and unauthenticated clients get `-NOAUTH` for every non-`no_auth` command; `AUTH` / `HELLO … AUTH` validate with a compare whose time does not depend on the password's content, though it can reveal the password's length (item 61). Only `requirepass` sets a password: config-file `user`, `aclfile` and `include` lines are ignored (item 24). **protected-mode** is on by default, so a server with no password refuses non-loopback clients. `MODULE LOAD` (which runs arbitrary native code) is gated behind `enable-module-command` (default off), `rename-command` can neutralise dangerous verbs, and `proto-max-bulk-len`/multibulk + query-buffer caps bound a malicious client's memory. `DEBUG` is open to every authenticated client, where Redis 7.2.5 needs `enable-debug-command` (item 61). To disable it, put `rename-command DEBUG` (with no target) in the config file: the Redis form `rename-command DEBUG ""` does not disable a command in PeaDB, and Redis refuses the PeaDB form (item 24). `ACL WHOAMI`/`USERS`/`LIST`/`CAT`/`GETUSER`/`GENPASS`/`HELP` truthfully report the single `default` user (password shown as `#<sha256-hex>` of `requirepass`, or `nopass`); `ACL SETUSER`/`DELUSER`/`LOAD`/`SAVE`/`LOG`/`DRYRUN` refuse with an error naming the gap rather than applying, discarding, or faking a rule. **Still missing:** a multi-user **ACL** rule engine and **TLS** — terminate TLS at a proxy and keep multi-tenant isolation at the network layer until both land.
- **Memory pressure & eviction** — `maxmemory` sets a byte limit (with `100mb`/`2gb` unit parsing in both config and `CONFIG SET`), but it does not keep process memory under that limit today (see the used-memory note below). When used memory exceeds it, PeaDB **evicts** keys per `maxmemory-policy` — all eight Redis modes: `noeviction` (default), `allkeys-lru`/`-lfu`/`-random`, and `volatile-lru`/`-lfu`/`-random`/`-ttl`. Eviction uses approximate sampling (`maxmemory-samples`, default 5) over a random bucket walk across all DBs (or only TTL-bearing keys for `volatile-*`); the chosen victim is evicted, counted in `evicted_keys`, propagated as a `DEL` to replicas and the AOF, and emits an `evicted` keyspace notification. With `noeviction` (or when a `volatile-*` policy has no eligible keys) writes are rejected with `-OOM …` instead — today every write, including `DEL`, `UNLINK` and `EXPIRE`, because PeaDB has no `denyoom` flag yet, so a full server can only be cleaned up with `FLUSHALL`/`FLUSHDB` or a higher `maxmemory` (item 39). Used memory is an estimate from a full walk of every key, cached for about 100 ms (the eviction loop lowers it as it frees). It is too low for collections, because it leaves out container and allocator overhead, and with `maxmemory` set, once one walk takes 100 ms or more (about 2M keys) every write walks again and writes slow to a few per second (item 38). LRU/LFU metadata is approximate (a coarse access clock / log-increment counter touched on the command's primary key). `stop-writes-on-bgsave-error` (default on) additionally rejects writes with `-MISCONF` when a background save or AOF write is failing.
- **Monitoring** — there is no HTTP `/metrics` endpoint, but the standard tooling works: `INFO` (community exporters such as `redis_exporter` scrape it) now reports real `blocked_clients`, `used_memory_rss`/`mem_fragmentation_ratio`, `used_memory_peak`, `used_cpu_*`, `latest_fork_usec`/`total_forks`, `instantaneous_ops_per_sec`, and `pubsub_channels`. About 16 standard fields are still missing (for example `run_id`, `rejected_connections`, `aof_last_write_status` and the per-replica `slaveN:` lines), so some exporter alerts never fire and Redis Sentinel cannot manage PeaDB (item 22), and every INFO call walks the whole keyspace, so frequent scrapes of a large instance stall every client (item 55). `SLOWLOG` is **populated** (real per-command timing via `slowlog-log-slower-than`/`slowlog-max-len`), `INFO commandstats` reports real `usec`/`usec_per_call`, `LATENCY LATEST`/`HISTORY`/`RESET`/`DOCTOR` work (gated by `latency-monitor-threshold`), `MONITOR` streams live commands, `CLIENT LIST`/`CLIENT KILL` (by `ID`/`ADDR`) and runtime `CONFIG SET loglevel` work. **Keyspace notifications** (`notify-keyspace-events`, `__keyspace@`/`__keyevent@`, incl. `expired`) are implemented.
- **Connections** — accepted client sockets get `TCP_NODELAY` + `SO_KEEPALIVE` (so half-open peers are detected and reaped). An idle-client `timeout` (seconds; config/CLI/`CONFIG SET`, default 0 = off) closes clients idle past the window; replicas, blocked/`WAIT`ing/`MULTI` clients and pub/sub subscribers are exempt. `client-output-buffer-limit` is enforced per class (`normal`/`slave`/`pubsub`) with Redis-default hard/soft/soft-seconds (normal unlimited; replica 256mb/64mb/60; pubsub 32mb/8mb/60): a slow consumer or lagging replica whose buffer exceeds its limit is disconnected instead of OOMing the single process.
- **Cluster configuration** — cluster mode is **experimental and not production-safe** ([`compat/delta.md`](../compat/delta.md) items 6 and 64–67). `cluster-enabled` (config/CLI, default `no`) is startup-only, like Redis's own `IMMUTABLE_CONFIG` treatment of the same parameter; `CONFIG SET cluster-enabled` is refused. `cluster-announce-ip`/`-port`/`-bus-port` (config/CLI/`CONFIG SET`) name the address/ports this node advertises to peers and clients; an unset announce-ip falls back to `bind`, a documented simplification of Redis's live-connection auto-detection (see [`docs/decisions/p5-cluster-addressing-and-version-provenance.md`](decisions/p5-cluster-addressing-and-version-provenance.md) for the full rationale). Because that fallback would otherwise announce an unreachable wildcard address, a node started with `cluster-enabled yes` **refuses to start** if the resolved announced host is `0.0.0.0`, `::`, `*`, or empty — whether that resolution comes from the `bind` fallback or from an explicit `cluster-announce-ip` naming a wildcard itself — set `cluster-announce-ip` to a real, peer-reachable address for any node bound to a wildcard address (including the shipped `Dockerfile`, which binds `0.0.0.0`). `CONFIG SET cluster-announce-ip` refuses the same wildcard values at runtime, matching the startup guard. `redis_mode` in `INFO` and the `cluster_enabled` field (in both `# Server` and `# Cluster`) all derive from the same `cluster-enabled` state, so they cannot disagree. The cluster bus listener (port + 10000) only opens when `cluster-enabled yes`.
- **TLS** — not supported; terminate TLS at a proxy (stunnel, Envoy, a cloud load balancer).
- **OS** — Linux is the primary target (kernel 5.15+ enables the optional io_uring backend); GCC 11+/Clang 14+ and CMake ≥ 3.16. Windows is a non-goal for production.
