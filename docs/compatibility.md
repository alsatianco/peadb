# PeaDB Compatibility & Migration

PeaDB targets **Redis 7.2.5** (commit `f60370ce28b946c1146dcea77c9c399d39601aaa`); behavior, error messages, and edge cases are validated against that exact version. [`../compat/delta.md`](../compat/delta.md) is the **canonical, always-current registry** of known gaps — this guide is a high-level orientation, not a substitute for it.

## Is it a drop-in replacement?

Not yet for data you cannot afford to lose. PeaDB speaks RESP2 (and basic RESP3) on port `6379`, and standard clients work unmodified for core workloads — strings, hashes, lists, sets, sorted sets, streams, transactions, Lua scripting, and pub/sub. Explicitly tested clients: `redis-py` 5.0.1, `node-redis` 4.6.13, `go-redis/v9` 9.5.1. `redis-cli`, `redis-benchmark`, `memtier_benchmark`, Jedis, and Lettuce also work.

But a verified review in 2026-10 found open defects that can lose or change data with no error: in RDB and AOF persistence, in replication, in `SCAN`, and on every migration path to and from Redis. They are [`compat/delta.md`](../compat/delta.md) items 24–74, and most are not fixed yet (each item says whether it is). Read them before you put data you need on PeaDB.

## Configuration

PeaDB loads its config file and command line the way `redis-server` 7.2.5 does: the same line splitting, setting names, aliases, value checks and error text, `include`, and `--name value` options parsed as config lines after the file. Where Redis's config loader refuses to start (a missing config file, an unknown name, the wrong number of arguments, a bad value or a bad `rename-command`), PeaDB refuses with the same reason and line. It also refuses the Redis settings it cannot honour safely, such as `user`, `aclfile`, `loadmodule`, `replicaof` and settings that turn TLS on, so a hardened redis.conf can no longer start PeaDB with no password or without TLS by mistake; like any setting, these are judged on their final value. Every other Redis setting that PeaDB does not apply yet is accepted with one warning for each in the log ([`compat/delta.md`](../compat/delta.md) item 24 lists them and the few Redis checks PeaDB does not make). The settings PeaDB applies are listed in the [README Configuration section](../README.md#configuration). Like Redis, PeaDB makes `dir` its working directory. `CONFIG GET` and `CONFIG SET` follow Redis 7.2.5 too: `CONFIG GET` reports every Redis setting and alias (hidden ones only by exact name), and `CONFIG SET` takes several settings at once, all or nothing, with Redis's error for an unknown name, an immutable or protected setting (`dir` and `dbfilename` need `enable-protected-configs`), a repeated name and a bad value. The settings PeaDB applies take effect at once, including `appendonly yes` (which starts the AOF with a rewrite of the data, as in Redis), `maxclients`, `proto-max-bulk-len` and `client-query-buffer-limit`; `port` and `bind` cannot change while PeaDB runs yet (item 25). A Redis setting that PeaDB does not apply either has a fixed value that describes what PeaDB always does, which `CONFIG GET` reports and `CONFIG SET` keeps (any other value is refused, for example `rdbcompression yes`), or it keeps the value it is given, has no effect, and gets a warning in the log, as in the config file (item 24). So a `CONFIG SET` that answers `OK` for a setting PeaDB applies has applied it. Changes are in memory only: `CONFIG REWRITE` is not supported yet (item 25), so runtime changes do not survive a restart.

## Live migration & rollback

**None of these paths works end to end today**; [`compat/delta.md`](../compat/delta.md) item 49 lists every defect, and it stays open until an acceptance test passes in both directions. The intended steps are below, each with the defect that breaks it now.

1. Start PeaDB beside the existing Redis master.
2. Run `REPLICAOF <redis-host> <redis-port>` — PeaDB performs a native in-process PSYNC2 full sync (RDB load, then a continuous command stream). Today this fails when the master needs more than about 1 s to produce its RDB, which is any real production dataset, and PeaDB cannot sync from a master whose default user is disabled, because it has no `masteruser` (item 50).
3. Wait until `INFO replication` shows the replica caught up.
4. Run `REPLICAOF NO ONE` on PeaDB and repoint application clients. Today a PeaDB replica does not write the data it received through replication to its own RDB or AOF, so after promotion its first restart loads only the writes made after the promotion (item 45).

To **roll back**, the plan is to export a Redis-readable RDB with `SAVE`/`BGSAVE` (or `scripts/redis/export_rdb_via_redis.py`) and load it into Redis. Since 2026-10-06 real Redis loads a PeaDB RDB and a real Redis replica of a PeaDB master completes its full sync (item 27, fixed), but not when the data holds streams (item 5), and `RESTORE` in PeaDB still refuses most of the encodings real Redis `DUMP` writes (item 51). For offline import and export, the bridge scripts are:

```bash
python3 scripts/redis/import_rdb_via_redis.py <dump.rdb>     # Redis RDB -> PeaDB
python3 scripts/redis/export_rdb_via_redis.py <output.rdb>   # PeaDB -> Redis RDB
```

The bridge scripts use a temporary Redis instance. They have no password option and do not check replies, so against a server with `requirepass` they copy nothing and still exit 0; they also copy only database 0 and skip consumer groups and functions (item 52). Check the key counts on both sides after every run. **Streams** persist and replicate within PeaDB (PSYNC full-sync handles stream datasets), but PeaDB's stream RDB encoding is PeaDB-specific — a real `redis-server` cannot load a PeaDB RDB that contains streams (item 5). No cross-engine stream path is complete: the bridge scripts drop consumer groups, and loading a PeaDB AOF into Redis has not been tested (item 49).

## Feature status at a glance

See [`../compat/delta.md`](../compat/delta.md) for authoritative, per-feature detail. The table shows what is implemented, not what is free of defects: the open defects behind each row are in delta items 24–74 (for example, `SCAN` can miss keys while the keyspace grows, item 32).

| Works | Partial / surface | Not yet |
|-------|-------------------|---------|
| Strings, hashes, lists, sets, sorted sets, streams (RDB + replication) | Streams — full PEL, blocking XREAD/XREADGROUP, XCLAIM/XAUTOCLAIM, `XINFO STREAM/GROUPS/CONSUMERS`; consumer seen/active times don't survive an RDB round-trip | TLS (use a TLS-terminating proxy) |
| Transactions — `MULTI`/`EXEC`/`WATCH` (optimistic locking) | RESP3 — `HELLO` negotiates; `HGETALL` returns maps and the map/set/double/bool encoders exist, but many replies are still RESP2-shaped | Multi-user ACL rules |

## Persistence & durability

PeaDB offers Redis's durability options, but not yet Redis's durability: open defects can lose acknowledged writes or stop the next restart ([`compat/delta.md`](../compat/delta.md) items 27–37, most not fixed yet). The bullets below name the main ones.

- **RDB snapshots** — `SAVE` (blocking) and `BGSAVE` (forked) write an RDB in Redis's format, with Redis's CRC64 checksum, to `--dir`/`--dbfilename`, and PeaDB loads the RDB files real Redis 7.2.5 writes (item 27 is fixed). Lists of any length are saved in nodes the way Redis splits them by `list-max-listpack-size` (item 29, fixed), and `SAVE` is refused while a `BGSAVE` runs. A `BGSAVE` that fails, including a failed `fork()`, is logged with Redis's lines and sets `rdb_last_bgsave_status:err`, so with save points writes are refused with `-MISCONF` until a save succeeds; `rdb_last_save_time`, `LASTSAVE` and `rdb_changes_since_last_save` move only after a good save; `FLUSHALL` stops a running `BGSAVE` and, with save points, saves the empty dataset at once; a `BGSAVE` inside `MULTI`/`EXEC` runs after `EXEC`, and one during an AOF rewrite is refused or, with `BGSAVE SCHEDULE`, run after it (item 34, fixed 2026-10-06; a `BGREWRITEAOF` during a `BGSAVE` still starts a second child, item 3). A file with the encodings that only Redis before 7.0 writes (zipmaps and ziplists, which Redis 3.2 to 6.2 also used for every list) stops startup with a clear error: load it in Redis 7 and save it again (item 53). The writer fsyncs the file and its parent directory and fails the save on any fsync error rather than leaving a corrupt snapshot. Every load checks the trailing **CRC64**, as Redis does (PeaDB checks it before it replaces the data in memory, Redis after reading the keys): on startup a corrupt native RDB (`REDIS` magic, bad checksum) is fatal — the server refuses to start rather than silently falling back to an empty/legacy load — and a replica whose full-sync RDB fails the check keeps its data and retries the sync. As in Redis, `rdbchecksum no` (startup only) skips the check and saves a zero checksum, and a file with a zero checksum loads without a check. A file cut short is refused even then. This is also how to load a `dump.rdb` written by PeaDB before 2026-10-06, whose checksum used the wrong table: start PeaDB once with `--rdbchecksum no`, run `SAVE`, and restart without it. An AOF written by that older PeaDB that holds `RESTORE` or `FUNCTION RESTORE` lines stops startup; run `BGREWRITEAOF` on the older PeaDB before upgrading.
- **AOF** — enable with `--appendonly yes`; commands append to a persistent fd. The `appendfsync` policy governs durability:

  | `appendfsync` | Behavior | Worst-case loss on crash |
  |---------------|----------|--------------------------|
  | `always` | fsync after every write | none while every write and fsync succeeds; today a failed write or fsync is still answered `OK`, where Redis exits (item 35) |
  | `everysec` *(default)* | fsync ~once per second | ~1 second of writes |
  | `no` | flushing left to the OS | OS-buffer dependent |

  `BGREWRITEAOF` forks a child to rewrite, then the parent atomically renames the result over the live file. `appendfsync always`/`everysec` check the `fsync()` return and flag a write error, after which writes are refused with `-MISCONF`; nothing clears that flag, so the server stays read-only until a restart (item 35). On startup a **truncated AOF tail** (a crash in the middle of the last write) is cut off the file at the last whole command and logged, as Redis does with `aof-load-truncated yes` (the default), so later writes follow good data and the next restart loads them (before 2026-10-06 the file was not cut and the next restart failed, item 30); with `aof-load-truncated no` the server refuses to start instead. **Bytes that are not a command are fatal** wherever they are — the server refuses to start rather than serve partial data. Transactions and scripts are not wrapped in `MULTI`/`EXEC` in the AOF, so a crash can replay half a transaction (item 36). With the AOF on, startup loads only the AOF, as Redis does, so a `dump.rdb` in `--dir` is not loaded as well (before 2026-10-06 it was, and every write was applied twice, item 28). This is also true when the AOF is empty or new: turning on `appendonly yes` in the config of a server that has only a `dump.rdb` starts it with no data (PeaDB logs a warning naming the file). To move an RDB dataset to the AOF, start with the AOF off and run `CONFIG SET appendonly yes`, which writes the data into the AOF. An AOF that cannot be opened stops startup, as in Redis.
- **Save points** — `save <seconds> <changes>` (config or `CONFIG SET save`, repeatable; `save ""` disables) trigger a background `BGSAVE` when enough keys changed within the window, and `SHUTDOWN [SAVE|NOSAVE]` saves on a clean shutdown when save points are configured. SIGTERM (what `systemctl stop`, `docker stop` and Kubernetes send) and SIGINT shut down the same way, with the flags of `shutdown-on-sigterm`/`shutdown-on-sigint`, and a second SIGINT exits at once without saving; SIGHUP is ignored, as in Redis. A shutdown first stops a running `BGSAVE` child. `SHUTDOWN` answers and logs like Redis's, including `SHUTDOWN ABORT` (it cancels a signal not acted on yet), a failed save that keeps the server running, and `FORCE`. A shutdown does not wait for lagging replicas yet (no `shutdown-timeout`, item 33), so stop writes and check `WAIT` before you stop a master whose replicas must have every write. The default ships **no** save points (set them, or enable AOF, to persist) — so an out-of-the-box instance with neither is non-durable, exactly like Redis started with `save ""` and `appendonly no`.
- **Streams** — persist via both **RDB** (entries + consumer groups + full PEL, PeaDB-internal encoding) and AOF, and replicate through PSYNC. A PeaDB RDB containing streams is not loadable by real Redis (PeaDB-specific stream type); use AOF/bridge for cross-engine stream migration.

## Operational notes

- **Security** — default-user authentication is enforced: set `requirepass` (config/CLI/`CONFIG SET`) and unauthenticated clients get `-NOAUTH` for every non-`no_auth` command; `AUTH` / `HELLO … AUTH` validate with a compare whose time does not depend on the password's content, though it can reveal the password's length (item 61). Only `requirepass` sets a password: a config with `user` or `aclfile` lines refuses to start, because there are no ACL users (item 24). **protected-mode** is on by default, so a server with no password refuses non-loopback clients. `MODULE LOAD` (which runs arbitrary native code) is gated behind `enable-module-command` (default off), `rename-command` can neutralise dangerous verbs, and `proto-max-bulk-len`/multibulk + query-buffer caps bound a malicious client's memory. `DEBUG` is open to every authenticated client, where Redis 7.2.5 needs `enable-debug-command` (item 61). To disable it, put `rename-command DEBUG ""` in the config file, as in Redis; `enable-debug-command no` stops startup instead, because PeaDB cannot apply it yet (item 24). `ACL WHOAMI`/`USERS`/`LIST`/`CAT`/`GETUSER`/`GENPASS`/`HELP` truthfully report the single `default` user (password shown as `#<sha256-hex>` of `requirepass`, or `nopass`); `ACL SETUSER`/`DELUSER`/`LOAD`/`SAVE`/`LOG`/`DRYRUN` refuse with an error naming the gap rather than applying, discarding, or faking a rule. **Still missing:** a multi-user **ACL** rule engine and **TLS** — terminate TLS at a proxy and keep multi-tenant isolation at the network layer until both land.
- **Memory pressure & eviction** — `maxmemory` sets a byte limit (with `100mb`/`2gb` unit parsing in both config and `CONFIG SET`), but it does not keep process memory under that limit today (see the used-memory note below). When used memory exceeds it, PeaDB **evicts** keys per `maxmemory-policy` — all eight Redis modes: `noeviction` (default), `allkeys-lru`/`-lfu`/`-random`, and `volatile-lru`/`-lfu`/`-random`/`-ttl`. Eviction uses approximate sampling (`maxmemory-samples`, default 5) over a random bucket walk across all DBs (or only TTL-bearing keys for `volatile-*`); the chosen victim is evicted, counted in `evicted_keys`, propagated as a `DEL` to replicas and the AOF, and emits an `evicted` keyspace notification. With `noeviction` (or when a `volatile-*` policy has no eligible keys) writes are rejected with `-OOM …` instead — today every write, including `DEL`, `UNLINK` and `EXPIRE`, because PeaDB has no `denyoom` flag yet, so a full server can only be cleaned up with `FLUSHALL`/`FLUSHDB` or a higher `maxmemory` (item 39). Used memory is an estimate from a full walk of every key, cached for about 100 ms (the eviction loop lowers it as it frees). It is too low for collections, because it leaves out container and allocator overhead, and with `maxmemory` set, once one walk takes 100 ms or more (about 2M keys) every write walks again and writes slow to a few per second (item 38). LRU/LFU metadata is approximate (a coarse access clock / log-increment counter touched on the command's primary key). `stop-writes-on-bgsave-error` (default on) additionally rejects writes with `-MISCONF` when a background save has failed and save points are set (then `PING` too, as in Redis), or when an AOF write is failing.
- **Monitoring** — there is no HTTP `/metrics` endpoint, but the standard tooling works: `INFO` (community exporters such as `redis_exporter` scrape it) now reports real `blocked_clients`, `used_memory_rss`/`mem_fragmentation_ratio`, `used_memory_peak`, `used_cpu_*`, `latest_fork_usec`/`total_forks`, `instantaneous_ops_per_sec`, and `pubsub_channels`. About 16 standard fields are still missing (for example `run_id`, `rejected_connections`, `aof_last_write_status` and the per-replica `slaveN:` lines), so some exporter alerts never fire and Redis Sentinel cannot manage PeaDB (item 22), and every INFO call walks the whole keyspace, so frequent scrapes of a large instance stall every client (item 55). `SLOWLOG` is **populated** (real per-command timing via `slowlog-log-slower-than`/`slowlog-max-len`), `INFO commandstats` reports real `usec`/`usec_per_call`, `LATENCY LATEST`/`HISTORY`/`RESET`/`DOCTOR` work (gated by `latency-monitor-threshold`), `MONITOR` streams live commands, `CLIENT LIST`/`CLIENT KILL` (by `ID`/`ADDR`) and runtime `CONFIG SET loglevel` work. **Keyspace notifications** (`notify-keyspace-events`, `__keyspace@`/`__keyevent@`, incl. `expired`) are implemented, but many write commands send no event or the wrong one: for example a pop that empties a key sends no `del`, and LMOVE, SMOVE and the store commands send nothing (item 72).
- **Connections** — accepted client sockets get `TCP_NODELAY` and, unless `tcp-keepalive` is `0`, TCP keepalive probes after `tcp-keepalive` seconds of silence (Redis's default 300), so half-open peers are detected and reaped. An idle-client `timeout` (seconds; config/CLI/`CONFIG SET`, default 0 = off) closes clients idle past the window; replicas, blocked/`WAIT`ing/`MULTI` clients and pub/sub subscribers are exempt. `client-output-buffer-limit` is enforced per class (`normal`/`slave`/`pubsub`) with Redis-default hard/soft/soft-seconds (normal unlimited; replica 256mb/64mb/60; pubsub 32mb/8mb/60): a slow consumer or lagging replica whose buffer exceeds its limit is disconnected instead of OOMing the single process.
- **Cluster configuration** — cluster mode is **experimental and not production-safe** ([`compat/delta.md`](../compat/delta.md) items 6 and 64–67). `cluster-enabled` (config/CLI, default `no`) is startup-only, like Redis's own `IMMUTABLE_CONFIG` treatment of the same parameter; `CONFIG SET cluster-enabled` is refused. `cluster-announce-ip`/`-port`/`-bus-port` (config/CLI/`CONFIG SET`) name the address/ports this node advertises to peers and clients; an unset announce-ip falls back to `bind`, a documented simplification of Redis's live-connection auto-detection (see [`docs/decisions/p5-cluster-addressing-and-version-provenance.md`](decisions/p5-cluster-addressing-and-version-provenance.md) for the full rationale). Because that fallback would otherwise announce an unreachable wildcard address, a node started with `cluster-enabled yes` **refuses to start** if the resolved announced host is `0.0.0.0`, `::`, `*`, or empty — whether that resolution comes from the `bind` fallback or from an explicit `cluster-announce-ip` naming a wildcard itself — set `cluster-announce-ip` to a real, peer-reachable address for any node bound to a wildcard address (including the shipped `Dockerfile`, which binds `0.0.0.0`). `CONFIG SET cluster-announce-ip` refuses the same wildcard values at runtime, matching the startup guard. `redis_mode` in `INFO` and the `cluster_enabled` field (in both `# Server` and `# Cluster`) all derive from the same `cluster-enabled` state, so they cannot disagree. The cluster bus listener (port + 10000) only opens when `cluster-enabled yes`.
- **TLS** — not supported; terminate TLS at a proxy (stunnel, Envoy, a cloud load balancer).
- **OS** — Linux is the primary target (kernel 5.15+ enables the optional io_uring backend); GCC 11+/Clang 14+ and CMake ≥ 3.16. Windows is a non-goal for production.
