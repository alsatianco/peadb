# PeaDB Architecture

How PeaDB works internally and how to develop it. For build/test commands and code conventions, see [`../CLAUDE.md`](../CLAUDE.md); for compatibility status, see [`../compat/delta.md`](../compat/delta.md).

## Execution model

PeaDB runs a **single-threaded event loop** (like Redis). One thread accepts connections, reads and parses requests, dispatches commands, and writes replies. The loop is built on an abstracted `Poller` (`include/poller.hpp`) backed by **epoll** on Linux and **kqueue** on macOS, with an optional **io_uring** backend compiled in when `PEADB_HAVE_IO_URING` is defined. The poller waits with a 100 ms timeout, which also bounds background housekeeping (active expiry, child reaping, blocked-client rechecks, deferred `WAIT`).

Besides the event-loop thread there are two helper threads: a detached **replica supervisor** that `REPLICAOF` starts, which runs the sync, reads the master's command stream and reconnects with backoff until a newer `REPLICAOF` replaces it (it only touches atomics and queues commands for the event loop), and a **lazyfree** worker that destructs large detached objects (`UNLINK`, `FLUSHALL`/`FLUSHDB ASYNC`) off the loop. Both preserve the single-writer invariant: command processing and `DataStore` mutation happen only on the event-loop thread, and the lazyfree worker only ever touches data that was first *moved out* of the live keyspace (exclusive ownership transferred under a mutex-guarded queue), so there is no fine-grained locking on the hot path and no race with live data.

## Data structures

Internal representations differ from Redis but preserve observable semantics:

- **`Entry` is a tagged union.** Each key's value is an `Entry` holding a `std::variant` over the string payload (inline, SSO) plus five heap-held collection payloads (`unique_ptr<HashT/ListT/SetT/ZSetT/StreamT>`), so **only the active type allocates**. The variant alternatives are ordered to match `ValueType`, so `Entry::type()` is just `payload.index()`. Inline fields accessed regardless of type — `expire_at_ms`, an `lru` clock/counter (reserved for eviction), and `string_force_raw` — sit outside the variant. Typed accessors (`str()`, `hash()`, `list()`, `set()`, `zset()`/`zord()`, `stream_*()`) lazily materialize the active alternative on the get-or-create paths; a hand-written deep-copy ctor/assign clones the active payload (a `unique_ptr` member makes the compiler-default copy ill-formed) so `COPY`/`RENAME`/`SWAPDB`/MULTI snapshots keep value semantics. This shrank `sizeof(Entry)` from ~328 B (libc++; ~456 B libstdc++, when every key carried all six empty payloads) to ~56 B, cutting accounted bytes/key ~3.9× and real RSS ~32% for the small-key workload. All payload access lives in `src/datastore.cpp`; `command.cpp`/`rdb.cpp`/`lua_engine.cpp` go through `DataStore` methods.
- **Hash tables are `Dict`s.** The keyspace of each database, the fields of a hash, the members of a set and the member-to-score map of a sorted set live in a `peadb::Dict` (`include/dict.hpp`), a chained hash table modelled on Redis's `dict.c`: the number of buckets is a power of two and an element's bucket is `hash & (buckets - 1)`; the first insert allocates 4 buckets, the table doubles when it holds as many elements as buckets, and it shrinks to the smallest power of two that holds every element when less than 10% of the buckets are used (a hash, set or sorted set right after a delete; a keyspace from `databases_cron()` in the event loop, not while a fork child runs). That layout is what lets `SCAN` keep Redis's guarantee (see SCAN below). The interface is the part of `std::unordered_map`/`std::unordered_set` that PeaDB uses, with the same rules for references and iterators; unlike them, `clear()` frees the bucket array. A resize moves every element at once; Redis rehashes in steps ([`../compat/delta.md`](../compat/delta.md) item 13). String keys are hashed with SipHash-1-2 under a key drawn at random when the process starts (`DictStringHash`), as Redis's `dictGenHashFunction()` does, so clients cannot choose keys that pile into one bucket; an erase through an iterator does not look for the next element (unlike `std::unordered_map::erase`), so it stays O(1) in a sparse table.
- **Strings / lists** — the string payload is a `std::string` inside the `Entry`; a list is a `std::deque`.
- **Sorted sets** — a dual structure: a `Dict<member,score>` for O(1) lookup plus a `std::map` keyed on `{score,member}` as an ordered score index, so `ZRANGE`/`ZRANGEBYSCORE` iterate the index instead of copy-and-sort.
- **Edits happen in place.** A command that changes a collection does it through a `DataStore` method that edits the payload of the existing `Entry` (for example `lset()`, `lrem()`, `linsert()`, `ltrim()`, `zrem()`), so the key keeps its `expire_at_ms` and `lru`, and the method deletes the key when the collection becomes empty, as Redis does. Deleting the key and writing it back drops the TTL: that was [`../compat/delta.md`](../compat/delta.md) item 31. Commands that replace the whole value (`SET` without `KEEPTTL`, the `*STORE` commands) drop the TTL on purpose, as in Redis.
- **Streams** — in-memory entries + consumer-group PEL; core ops work, advanced PEL features are partial.
- `OBJECT ENCODING` synthesizes Redis-style encoding names from element counts/sizes to mimic Redis's encoding-transition thresholds.

## Key expiry

Hybrid **lazy + active**, like Redis's `expireIfNeeded()` and `activeExpireCycle()`. A key is expired once the time is past its expire time (`now > when`). Lazy: a command that meets an expired key deletes it. Active: `active_expire_cycle()` runs at most every ~100 ms on a master, scanning up to 64 keys per database starting from a **randomly chosen bucket** (no front-bias / tail starvation).

Every deletion of an expired key goes through `DataStore::remove_expired()`, which calls the lazy-expire hook (`propagate_lazy_expire()` in `src/command.cpp`): the hook queues a `DEL` for the AOF and the replicas with `also_propagate()` and sends the `expired` keyspace event. Inside a command the `DEL` joins the command's execution unit, so a write that meets an expired key reaches the AOF and the replicas as `MULTI`, `DEL`, the write, `EXEC`, as in Redis; `SCAN`, `RANDOMKEY` and the active cycle send each `DEL` alone. Walks that only look at keys delete nothing: `KEYS` skips expired keys, `CLUSTER COUNTKEYSINSLOT`/`GETKEYSINSLOT` count them, and an RDB save writes them with their expire time (a master that loads the file leaves them out).

A replica never deletes an expired key itself (`DataStore::set_replica_expiry()`): a lookup hides the key from the command that met it and puts it back when the command's outermost execution unit ends, and the master's `DEL` deletes it, so a replica whose clock runs ahead, or whose stream lags, keeps every key its master kept alive. While `DataStore::LazyExpireDisabled` is held no key counts as expired: while the AOF or an RDB loads, while a replica applies its master's stream, while an RDB is written, and in the dispatch's own lookups after a handler (the canonical form of a propagated write and the keyspace-event checks). Redis takes one time per outermost command, PeaDB only per script or function ([`../compat/delta.md`](../compat/delta.md) item 75).

While `CLIENT PAUSE` stops expiry (as Redis's pause does, so a failover sees a fixed dataset), the active cycle does not run and a lookup that finds an expired key moves it into a per-database hidden map instead of deleting it (`DataStore::set_expire_paused()`): commands see it as missing, `DBSIZE` still counts it, and no `DEL` is propagated. When the pause ends the hidden keys go back into their database and expire normally, with their `DEL`.

## Eviction (maxmemory-policy)

`used_memory` is Redis's `zmalloc_used_memory()`: `src/zmalloc.cpp` replaces the global `operator new` and `operator delete`, and each allocation adds, each free takes away, the size the allocator gave the block (`malloc_usable_size()` on Linux, `malloc_size()` on macOS), in one relaxed atomic, so the count is exact, O(1) to read, and includes container, allocator and buffer overhead (Lua's own `realloc()` memory is not counted, as in Redis). The replication backlog ring is allocated whole but not zero-filled, and the part no write has reached is left out of `used_memory`, so it counts as it fills, like Redis's growing backlog; until the first replica attaches, `used_memory` leaves the whole ring out (Redis has no backlog before that). The cost is one size lookup and one atomic add per allocation and per free, as in Redis; PeaDB commands allocate more often than Redis's (most of a SET's blocks are argument copies for the replication backlog). The maxmemory step of `processCommand()` runs in `handle_command()` for each command a client sends (`maxmemory_refuses()`; not for the commands EXEC or a script runs, never for AOF replay, the master stream, or on a replica): `perform_evictions()` (Redis's `performEvictions()`) frees what is over the limit, measured as `used_memory` less what is not counted (the replicas' output buffers and the AOF buffers, `free_memory_not_counted()`, measured as the allocator sizes them, `zmalloc_string_bytes()`), by calling `DataStore::evict_one(policy, samples)` and counting the bytes each delete frees, for at most `maxmemory-eviction-tenacity`'s time limit (500 µs by default); then the eviction timer (`run_eviction_cycle()`, every event-loop pass, which does not sleep while it is on; also started by `CONFIG SET maxmemory`) goes on. If memory is still over, a `denyoom` command (Redis's flag from the generated metadata; `command_flags()` gives scripts and functions with declared flags `denyoom` unless they have `allow-oom` or `no-writes`), an EXEC whose transaction holds one, or any command queued inside MULTI gets `-OOM`; the result is saved in `g_pre_command_oom_state`, and a script's `denyoom` command is refused only if it was set and the script has not written yet (`script_refuses_for_oom()`, Redis's `scriptVerifyOOM()`). The keyspace tables do not double when the new bucket array would go over `maxmemory` at up to 1.618 keys per bucket (`KeyspaceExpandAllowed`, Redis's `dictExpandAllowed()`). `evict_one` samples up to `maxmemory-samples` (default 5) candidate keys via the same random-bucket walk `RANDOMKEY` uses — across **all** DBs for `allkeys-*`, restricted to TTL-bearing keys for `volatile-*` — and picks the victim by the policy: oldest access clock (LRU), lowest frequency counter (LFU; a new key starts at Redis's `LFU_INIT_VAL`, 5), soonest TTL (`volatile-ttl`), or random; there is no eviction pool across calls, as Redis has ([`../compat/delta.md`](../compat/delta.md) item 12). Per-key LRU/LFU metadata rides in the inline `Entry::lru` word (a coarse ms clock, or an 8-bit log-increment counter), touched on `DataStore::get()` and at the dispatch chokepoint for the command's primary key — an O(1), first-key approximation. Each eviction is propagated like a server-issued deletion (a `DEL` to the replication backlog and AOF, each after a `SELECT` of the key's database, plus an `evicted` keyspace notification) and counted in `evicted_keys`.

## SCAN

`SCAN`, `HSCAN`, `SSCAN` and `ZSCAN` follow Redis's `scanGenericCommand()` (`DataStore::scan()`, `hscan()`, `sscan()`, `zscan()`). The cursor is Redis's `dictScan()` cursor (`Dict::scan()`): it names a bucket by the low bits of the hash and moves on by incrementing its bits in reverse order. Because a bucket of a table of 2^n buckets splits into two neighbouring buckets in that order when the table doubles, and two buckets merge when it halves, every element that is present for the whole scan is returned at least once, however much the table grows or shrinks between calls; an element can come more than once. One call visits buckets until it has looked at `COUNT` elements (before the `MATCH` filter), has visited `COUNT` × 10 more buckets, or has reached the end, so a `MATCH` or `TYPE` that matches nothing costs about `COUNT` buckets, not a walk of the whole table. Then `SCAN` deletes the expired keys it met that match its pattern, as Redis does; with `TYPE` it looks each key up like a read (expiring it, counting a keyspace hit or miss) and keeps only keys of that type. An erase never resizes a table, so those deletions cannot move keys under the cursor. A hash, set or sorted set that PeaDB reports with a small encoding (listpack or intset, as `OBJECT ENCODING` reports) is returned whole in one call with cursor 0, as Redis returns those encodings: an intset in ascending order and a sorted set in score order, as Redis keeps them (a small hash or set in table order, where Redis keeps insertion order, item 13). `MATCH` uses `fnmatch()`, which differs from Redis's matcher for a few patterns ([`../compat/delta.md`](../compat/delta.md) item 76).

## Persistence

- **RDB** — `SAVE` blocks; `BGSAVE` forks a child while the parent keeps serving. The writer fsyncs the file **and** its parent directory and fails the save on any fsync error. `BGSAVE` tracks the child PID, reaps it via `waitpid(WNOHANG)` in the loop, refuses a second `BGSAVE` while one runs, and reports `rdb_bgsave_in_progress` / `rdb_last_bgsave_status` / `rdb_last_bgsave_time_sec` / `rdb_saves` via `INFO`. Both children are made by `fork_child()` (Redis's `redisFork()`): the child closes its copies of the listening and client sockets (so a crash of the parent frees the port at once) and logs through a lock-free path (`log_in_forked_child()`), because another thread may have held the log lock at the fork. The status follows Redis's `rdbSaveBackground()` and `backgroundSaveDoneHandlerDisk()`: a failed `fork()` or child sets it to `err` (then writes get `-MISCONF` while save points are set, and the save points retry only 5 s after the last try), and the save time and the change count move only after a good save. Like Redis, a `BGSAVE` waits while an AOF rewrite runs (`BGSAVE SCHEDULE`) and a `BGSAVE` inside `EXEC` runs after it, so a snapshot never holds half a transaction; `FLUSHALL` stops a running `BGSAVE` and saves at once when save points are set. Every save writes `temp-<pid>.rdb` and renames it over the dump, like Redis's `rdbSave()`, so the `BGSAVE` child, a foreground `SAVE` and a shutdown's final save never share a file; `SAVE` is refused while a `BGSAVE` runs ([`../compat/delta.md`](../compat/delta.md) item 34). A `BGREWRITEAOF` can still start beside a running `BGSAVE` (item 3). The trailing checksum is Redis's CRC-64 (`crc64()` in `src/rdb.cpp`, 8 bytes per step like Redis's `crcspeed.c`), checked before any load changes the dataset, so real Redis and PeaDB load each other's files. A list is written as Redis's quicklist: `write_quicklist()` splits it into listpack nodes the way Redis's `quicklistPushTail()` does for `list-max-listpack-size`, so no node's 16-bit entry count can overflow (item 29), and the loader checks each listpack like Redis's `lpValidateIntegrity()`. The encodings of Redis before 7.0 (zipmap, ziplist) are refused (item 53).
- **AOF** — appends to a persistent fd opened once at startup. `appendfsync` is `always` (fsync per write), `everysec` (default; fsync ~1/s), or `no`. `BGREWRITEAOF` forks a child that writes a temp file; the parent appends the diff buffer and **atomically renames** over the live AOF, surfacing failures via `aof_last_bgrewrite_status`. With the AOF on, startup loads only the AOF and never the RDB as well, like Redis's `loadDataFromDisk()` (item 28, fixed). The loader reads the AOF like Redis's `loadSingleAppendOnlyFile()` and cuts a torn last command (or an unfinished `MULTI`) off the file, so later appends follow good data (item 30, fixed). A failed write or `everysec` fsync follows Redis's `flushAppendOnlyFile()` (`flush_append_only_file()` and `aof_cron()`): the bytes that are not in the file wait in `g_aof_buf` and are written again on every event-loop pass, writes get `-MISCONF` until that works, and under `always` the server exits before the reply goes out (item 35, fixed). Writes are propagated like Redis's `alsoPropagate()`/`propagatePendingCommands()`: the writes of a command and of the commands it runs (`EXEC`, scripts, functions, a woken blocked command) are queued while it runs (an `ExecutionUnit` around each command) and then written to the AOF and the replication backlog, each in one write, wrapped in `MULTI`/`EXEC` when there is more than one, so a crash or a cut link never applies half of a transaction (item 36, fixed). As Redis's `call()` propagates only a command that moved `server.dirty`, a write handler that changed nothing (a `SET` stopped by `NX` or `XX`, a `SETNX` or `MSETNX` answered 0, a `GETEX` that set or removed no TTL, a `GETDEL`, `SETRANGE`, `PERSIST` or `SORT` that changed nothing) sets `g_write_changed_nothing`, and the dispatch then neither propagates it nor counts it as a change nor sends its keyspace events (item 41, fixed). One child runs at a time: `BGREWRITEAOF` and `CONFIG SET appendonly yes` during a `BGSAVE` or inside `EXEC` set `aof_rewrite_scheduled`, and the cron starts the rewrite once no child runs and the transaction is in the AOF (item 3).
- **Shutdown** — the `SHUTDOWN` command and SIGTERM/SIGINT share `prepare_for_shutdown()` in `src/command.cpp` (Redis's `prepareForShutdown()` and `finishShutdown()`): stop a `BGSAVE` child (and delete its temp file) or an AOF rewrite child, fsync the AOF, do the final save when save points are set, and keep running with an error logged when that save fails, unless `FORCE`. Like Redis's `prepareForShutdown()`, a master whose replicas have not acknowledged the whole replication stream (without `NOW`, with `shutdown-timeout` not 0) first waits for them: it sends `REPLCONF GETACK *`, pauses writes, key expiry and eviction with a pause of its own (`kPauseDuringShutdown`, next to CLIENT PAUSE's `kPauseByClientCommand`; what is paused is all purposes together, as in Redis's `pauseActions()`), and blocks each `SHUTDOWN` client (`SessionState::blocked_on_shutdown`; server.cpp holds its later input). The signal handler only logs and sets a flag (async-signal-safe); `shutdown_cron()` runs at the top of every event-loop pass (Redis's `serverCron()` part): it starts the shutdown a signal asked for, with the `shutdown-on-sigterm`/`-sigint` flags, and finishes a waiting one (`finish_shutdown()`) once every replica's ACK offset is the master's offset or `shutdown-timeout` has passed. When the finish fails or `SHUTDOWN ABORT` cancels the wait, `cancel_shutdown()` ends the pause and answers the blocked clients through `g_reply_blocked_on_shutdown_cb`; server.cpp then runs what they sent after it. Once a shutdown succeeds no other command runs, the listeners close first and the replicas get a best-effort flush. A second SIGINT exits at once with code 1 ([`../compat/delta.md`](../compat/delta.md) item 33).
- **Streams + RDB** — streams are RDB-encoded under a PeaDB-specific type byte (entries + last-id + consumer groups + full PEL), so `SAVE`/`BGSAVE` and PSYNC full-sync handle stream datasets. The encoding is PeaDB-internal (not Redis's `RDB_TYPE_STREAM_LISTPACKS_3` byte layout), so a PeaDB RDB containing streams is not loadable by a real `redis-server`; cross-engine stream migration uses AOF or the bridge scripts. Streams also persist through AOF (replayed as `XADD`s).

## Replication

`REPLICAOF` runs a **native in-process PSYNC2 client** (`replica_do_fullsync`): TCP connect → `PING` → `REPLCONF` → `PSYNC` → RDB load → continuous command stream, with `+CONTINUE` partial resync served from a **configurable circular backlog** (`g_repl_backlog`, tracked by `g_master_repl_offset`). The **replication id is randomized per process** (`init_replication_id`), so unrelated instances never share a replid and can't be wrongly partial-resynced against a foreign stream; on promotion (`REPLICAOF NO ONE`) the old id rotates into `replid2`/`second_repl_offset` so a former sibling can still partial-resync against history. `INFO` reports `sync_full`/`sync_partial_ok`/`sync_partial_err`. Replicas emit `REPLCONF ACK` ~once per second, and a client `WAIT` injects `REPLCONF GETACK *` into the stream so replicas ACK within ~1 RTT instead of waiting for the next heartbeat. `min-replicas-to-write` can reject writes. A generation-tagged supervisor **auto-reconnects** with backoff; automatic failover (Sentinel/Raft) is not yet implemented. PeaDB's own replicas always send `PSYNC ? -1`, so for them every reconnect is a full sync, and the master builds that RDB in memory on the event loop ([`../compat/delta.md`](../compat/delta.md) items 46–47). Open defects can make a replica silently differ from its master: writes larger than the backlog in one loop pass, `RESTORE` with a TTL, replicated writes refused by client-side checks, ACKs sent before apply, no persistence on the replica, and `XCLAIM`/`XAUTOCLAIM` replayed as sent (items 40, 42–45 and 48).

## Cluster

Cluster mode is **experimental and not production-safe** ([`../compat/delta.md`](../compat/delta.md) items 6 and 64–67): routing hashes only a command's first key, so multi-key commands, transactions and scripts can write keys on the wrong node; there is no `CROSSSLOT` or `CLUSTERDOWN`; a restarted node serves slots that other nodes own; and `redis-cli --cluster` workflows do not work. Running `REPLICAOF` on top of cluster mode loses writes today, because a cluster-enabled replica drops replicated writes for slots it does not own while `WAIT` still counts it (item 43).

`CLUSTER` targets Redis 7.2's client-facing reply shapes — `SLOTS`/`SHARDS`/`NODES`/`INFO`, `MOVED`/`ASK` redirects naming the real owning node's advertised address — over a topology that is **operator-configured, not gossiped**: there is no cluster bus gossip protocol, no failure detection, no automatic failover, and no `nodes.conf` persistence, so a node's slot map is whatever `CLUSTER MEET`/`SETSLOT`/`ADDSLOTS(RANGE)` last told it and is lost on restart. Each node's 40-hex id is derived deterministically from its announced address (`sha1_hex`) rather than randomly generated and persisted, so it survives a restart with no state file to write or lose. PeaDB's cluster model has no replicas — every node is a singleton slot owner reporting `role:master`; `REPLICAOF` replication is a separate feature layered on top, not part of the slot map. The full rationale for these trade-offs — why gossip and automatic failover are deliberately out of scope for the customers PeaDB targets — is [`docs/decisions/p5-cluster-addressing-and-version-provenance.md`](decisions/p5-cluster-addressing-and-version-provenance.md); the current gap list against Redis's 27 canonical `CLUSTER` subcommands (PeaDB implements 15, plus the non-Redis `MEETBACK` extension) is [`compat/delta.md`](../compat/delta.md) item 6.

## Request/response handling

The parser slices the per-client input buffer as `string_view`. All replies for the commands parsed in one read are **batched into a single `WriteBuf`** and flushed with one `enqueue_output()`; partial writes register `EPOLLOUT` interest for backpressure. Blocking commands (`BLPOP`/`BRPOP`/`BLMOVE`/`BZPOPMIN`/`XREAD`) are served promptly: every successful write sets a pending-wakeup flag, and the loop rechecks blocked (and `WAIT`ing) clients **again after processing readable fds in the same iteration** — so a write and the unblock it triggers land together (sub-millisecond), instead of slipping to the next ~100 ms poll. (Cross-thread/eventfd wakeup for replica-applied writes and a per-key waiter index are possible refinements, deferred as diminishing-return.)

`CLIENT PAUSE` holds a command the way Redis's `blockPostponeClient()` does: `handle_command()` sets `SessionState::postponed` at the point where Redis checks the pause (after the checks that refuse a command), and the loop leaves that command and everything after it in the client's input buffer and stops reading commands from the client. Each loop pass checks whether the pause has ended (the poll timeout is cut to the pause's end time); when it ends, or becomes less strict, the held clients run their buffered commands again in the order they were held, before any new input is read. Which commands a write pause holds comes from Redis's own command flags (`WRITE`, `MAY_REPLICATE`), generated from the pinned command JSON into `include/command_metadata.generated.hpp`; a script or function is judged by the flags it declares. The replica's queue of commands from its master is held the same way.

## Design principles & roadmap

PeaDB treats **Redis as the executable specification**: where behavior is undocumented, Redis source defines truth, and deviations are tracked as explicit deltas in [`../compat/delta.md`](../compat/delta.md). Guiding rules: compatibility over elegance, determinism over cleverness, and continuous differential validation against a real Redis (`tests/diff/`).

The current implementation is the single-threaded baseline. The **target architecture** (not yet built) is a sharded, single-thread-per-shard model with lock-free inter-shard communication, io_uring-based async persistence, and locality-friendly custom allocators — preserving identical external semantics while scaling across cores. The `shard_loop.cpp` scaffolding (`crc16`, `key_hash_slot`, `ShardLoop`) is the first step.

Foundational decision records are archived under [`decisions/`](decisions/): the [Redis compatibility pin](decisions/d0-decisions.md) (7.2.5, auth/ACL scope, io_uring baseline, certification matrix) and the [module ABI boundary](decisions/m8-modules-abi.md).
