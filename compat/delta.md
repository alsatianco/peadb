# Compatibility Delta

Redis pin: 7.2.5 (`f60370ce28b946c1146dcea77c9c399d39601aaa`)

This file is the **canonical status registry** for PeaDB compatibility gaps.
README links should reference this document rather than repeating status.

Feature status labels:
- `full` — passes integration + differential tests including error shape
- `partial` — integration tests pass; differential or edge cases missing
- `surface` — command is registered and returns plausible output; no test coverage
- `stub` — command is registered but not implemented or returns hardcoded response
- `experimental` — implemented but not validated against Redis test suite

## Verification (the parity ratchet)

The PR workflow checks every C/C++ file in `src/` and `include/` with pinned clang-format 18.1.8 before building. The source baseline and generated command metadata follow that version; command discovery accepts whitespace and line breaks in registrations and is checked against the running command table; formatting changes do not change Redis compatibility status. Skipped build/test steps after a formatting failure provide no test evidence.

Parity is measured by two monotonically-improving numbers. Nightly CI and the local `scripts/run_all_tests.sh` both run the adopted suites natively, parse their results and enforce `check_suite_ratchet.py`. The local runner requires fresh, complete sweep logs and generates JSON/Markdown reports before checking the ratchet; [runner artifact and skip behavior](../scripts/README.md#running-scripts) is documented with the test workflow.

- **Upstream TCL pass-rate** — the official Redis 7.2.5 test suite runs in *native
  mode* (the harness spawns `peadb-server` as a redis-server stand-in via
  `SUITE_MODE=native scripts/redis/run_redis_tests.sh`). Per-suite results are parsed
  by `scripts/redis/parse_tcl_results.py` into `artifacts/redis-parity/pass_rate.json`;
  the rate is `Σok / Σ(ok + err + skipfile-lines)`, so skipping a test never improves
  the number. Adopted suites and their baselines live in
  `compat/redis_suite_ledger.json`.
- **Scoreboard `full` count** — `compat/commands.generated.md` statuses are
  proof-based (`full` = exercised by a green upstream suite AND differentially
  covered; see the generator header).

Ratchet rules (`scripts/ci/check_suite_ratchet.py`): any `[err]` in an adopted suite
fails; lowering a ledger count or growing a skipfile fails unless the same change
touches this file. Every skipfile line under `scripts/redis/skipfiles/` is a tracked
debt with a comment naming its delta item — the skipfiles themselves are the
authoritative debt list; each item below cites its skipfile where one exists.

Limits of this signal (found by the 2026-10 review): of the 26 upstream `integration/*` suites `integration/shutdown`, `integration/rdb`, `integration/replication-2`, `integration/block-repl`, `integration/replication-psync`, `integration/psync2` and `integration/logging` are adopted; the RDB suite explicitly skips startup client servicing (item 70) and Linux child COW/progress metrics (item 22). The larger replication suite, aof, corrupt-dump and the others are not, which is why the persistence and replication defects in items 27–47 pass every gate; and some upstream passes come from code shaped to match the test rather than real behavior (item 54; item 42's RESTORE propagation, which matched its upstream test only because of the braces, is fixed), so the pass rate overstates parity there.

Timed-suite accounting: unmodified Redis 7.2.5 `integration/psync2` repeats a ten-result cycle for 40 seconds, then runs two final checks. Policy `psync2-one-cycle-v1` validates every emitted cycle (sequential cycle numbers, master selection, four distinct non-master replica attachments, failover/load convergence and exactly four full syncs), requires both final checks and successful harness completion, and credits one full cycle plus those checks (`ok=12`). JSON retains `raw_ok` and `cycles`, also shown in Markdown; repeated cycles add stress evidence rather than distinct parity credit. Missing, skipped or unknown phases and all errors/exceptions fail parsing; a policy mismatch always fails the ratchet, even with a delta update. Other suites keep their existing counts. The six standard leak-tag ignores remain ignored, never passes; no PSYNC2 skipfile or upstream assertion changes are used.

## Known Deltas

1. ACL completeness
- Status: intentional temporary delta for early milestones M1-M3.
- Owner: security-compat
- Severity: high
- Target milestone: P4
- Implemented: basic AUTH/default user flow; a truthful ACL introspection surface
  (`WHOAMI`/`USERS`/`LIST`/`CAT`/`GETUSER`/`GENPASS`/`HELP`) against the single `default`
  user — see item 7 for the full description.
- Missing: full ACL user/rules engine. `SETUSER`/`DELUSER`/`LOAD`/`SAVE`/`LOG`/`DRYRUN` refuse
  with an error naming this gap rather than applying, discarding, or faking a rule (item 7).
- Tracking task: `M8` and later security-hardening milestones.

2. Redis RDB binary compatibility
- Status: temporary delta.
- Owner: persistence-compat
- Severity: high
- Target milestone: P3
- Implemented:
  - Native in-process RDB reader/writer for common Redis data types (see `rdb_load()` / `rdb_save()` usage at startup and in `SAVE`/`BGSAVE`). Its files load in real Redis 7.2.5 and real Redis files load in PeaDB (the checksum was fixed 2026-10-06, item 27; lists of any length since item 29 was fixed), including streams (item 5) and encodings from Redis before 7.0 (item 53).
  - RDB import/export via Redis bridge scripts (`scripts/redis/import_rdb_via_redis.py`, `scripts/redis/export_rdb_via_redis.py`). Authentication, checked replies and native all-database/type/function transfer are implemented (item 52); operational limits are in the migration guide.
  - Legacy PeaDB snapshot format as a fallback for local persistence.
  - Save points: `save <sec> <changes>` (config/`CONFIG SET`, repeatable; `save ""` disables)
    trigger a background BGSAVE via the event-loop cron; `SHUTDOWN [SAVE|NOSAVE]` saves on a
    clean shutdown. `stop-writes-on-bgsave-error` (default on) rejects writes with `-MISCONF`
    after a failed background save when save points are configured.
- Missing: full Redis RDB parity (broader opcode/encoding coverage, edge-case behavior, and rarely-used features). Default ships no save points (set them or enable AOF for durability). The reviewed native format defects are fixed in items 27/28/29/34/51/53; release-scale migration acceptance is tracked in item 49.
- Startup refuses unreadable, empty and invalid snapshot files with a fatal load diagnostic. Only an explicit `PEADB-SNAPSHOT-V1` header permits the legacy recovery reader; a legacy decoding failure is also fatal. CRC failures include Redis's `RDB CRC error` diagnostic. Native `integration/rdb` covers legacy encodings, streams, startup refusal, load counters and BGSAVE failure/recovery; `tests/integration/test_rdb_load_status_parity.py` additionally checks Redis-first refusal and counter reset/expiry behavior across databases, reloads and replica loads.
- Tracking: ongoing RDB parity hardening.

3. AOF binary/semantic parity gaps
- Status: temporary delta.
- Owner: persistence-compat
- Severity: medium
- Target milestone: P3
- Implemented: AOF append + startup replay + rewrite for supported commands.
  BGREWRITEAOF uses a parent-owns-rename design: the child writes a temp AOF and exits
  without renaming; the parent appends the diff buffer and only then atomically renames
  over the live AOF. Any failure (256 MiB diff cap, write/rename error, child crash)
  unlinks the temp file and leaves the old AOF intact on disk. Failure is surfaced via
  `INFO persistence aof_last_bgrewrite_status:err`; operators should rerun BGREWRITEAOF
  after addressing the cause (typically by reducing write pressure during the rewrite).
  Durability hardening: a failed AOF write or fsync is handled like Redis's
  `flushAppendOnlyFile()` (item 35: writes refused until it works again, exit under
  `appendfsync always`); startup
  tolerates a truncated AOF tail (`aof-load-truncated`, default yes, logged) but treats
  mid-file corruption as fatal (refuses to start); AOF rewrite serialises zset scores
  with `%.17g` (round-trip) instead of `std::to_string` (which lost precision each rewrite).
- Missing: full Redis-equivalent behavior/edge-case parity across entire command space. Open defects from the 2026-10 review (items 28, 30, 35 and 36, the RDB loaded under the AOF, the torn tail that was never cut off, the AOF write errors and the missing MULTI/EXEC framing, are fixed): the write cost on the event loop (item 58); no automatic rewrite (item 59). PeaDB's AOF is one file, not Redis 7's multi-part AOF (`appenddirname`, a base file, incr files and a manifest), so a Redis 7 `appendonlydir` cannot be loaded and the upstream test "MULTI with FLUSHALL and AOF", which reads the incr file, is skipped. Fixed 2026-10-07 (found 2026-10-06 against the pinned Redis while fixing item 34): Redis runs one child at a time, and so does PeaDB now for the AOF rewrite too: `BGREWRITEAOF` during a BGSAVE or inside `MULTI`/`EXEC` answers `Background append only file rewriting scheduled`, and `CONFIG SET appendonly yes` during a BGSAVE or inside `MULTI`/`EXEC` logs Redis's `AOF was enabled but there is already another background operation. An AOF background was scheduled to start when possible.` or `AOF was enabled during a transaction. An AOF background was scheduled to start when possible.`; the rewrite then starts from the cron once no child runs (`aof_rewrite_scheduled`, Redis's `serverCron()`). Before, they started a second child at once (twice the copy-on-write memory), and a rewrite started inside `EXEC` held half the transaction. PeaDB also schedules a `BGREWRITEAOF` that a script calls (Redis refuses it there, item 14), since a script's writes reach the AOF only when it ends. A fork that fails for `BGREWRITEAOF` now answers Redis's `Can't execute an AOF background rewriting. Please check the server logs for more information.` and sets `aof_last_bgrewrite_status:err` (it answered `BGREWRITEAOF failed: fork error`). The upstream `unit/multi` tests "MULTI with BGREWRITEAOF" and "MULTI with config set appendonly" are no longer skipped.
- Tracking tasks: broader compatibility hardening beyond current milestone.

5. Stream RDB encoding
- Status: `full` (native encoding fixed 2026-10-14 with item 51).
- Owner: persistence-compat
- Severity: medium
- Target milestone: P2
- Implemented: RDB v11/type 21 (`RDB_TYPE_STREAM_LISTPACKS_3`) for SAVE/BGSAVE, full sync and DUMP, with one shared native stream writer; a shared value decoder reads stream types 15/19/21 for RDB load and RESTORE. Entries (including duplicate/binary fields), empty streams, last/first IDs, entries-added/max-deleted history, group cursors/entries-read, consumers (including empty consumers and binary/empty names), seen/active times, and PEL IDs/owners/absolute delivery times/counts survive native snapshots. Deleted IDs may remain pending. Redis 7.2.5 reads PeaDB's snapshots and DUMP payloads, and full sync works in all four Redis/PeaDB pairings (`tests/integration/test_dump_native_interop.py`); redis-check-rdb validates the snapshots. Legacy native formats inherit consumer active-time from seen-time and reconstruct group read offsets as Redis does. Old private type 200 remains readable for local recovery; its unstored history/consumer metadata cannot be recovered. AOF rewrite reconstructs entries, history, groups and PEL effects through canonical commands (item 48).
- Missing: nothing for valid native stream snapshot interoperability. Macro-node layout and approximate trimming still differ (item 16), and AOF rewrite reconstructs consumer activity through commands, as Redis does. For invalid payloads, PeaDB validates stream listpack structure/counts/order and metadata and refuses duplicate/orphan/multiply-owned PEL IDs rather than represent corrupt structures that Redis's default shallow validation may accept.
- Tracking: complete; migration-scale acceptance is tracked in item 49.

6. Redis Cluster protocol surface
- Status: `experimental` — **not production-safe.** The 2026-10 review found that cluster mode can write keys on the wrong node, apply part of a transaction or script, and accept writes for slots other nodes own after a restart (items 64, 65, 66, 67). What exists: real per-node ownership, addressing, and Redis 7.2 reply shapes over an operator-configured topology; still no gossip, no failure detection, no automatic failover.
- Owner: cluster-compat
- Severity: critical
- Target milestone: P5
- Implemented: a stable node table (`g_cluster_nodes`) keyed by a 40-hex id derived deterministically from each node's announced address (`sha1_hex("peadb-cluster-node:" + host + ":" + port)`), stable across restarts without a `nodes.conf` file; real slot ownership (`g_slot_routes`/`g_slot_owner`) drives `ADDSLOTS`/`DELSLOTS`/`ADDSLOTSRANGE`/`DELSLOTSRANGE`/`SETSLOT NODE`, and `MOVED` redirects name the real owning node's announced `host:port`, not a hardcoded address. `SETSLOT MIGRATING`/`IMPORTING` do **not** write `g_slot_owner`/`g_slot_routes` — a slot in flight stays reported as owned by whoever owned it before the migration started, exactly like Redis keeping the slot in the owner's bitmap throughout migration; the redirect target instead lives in two side-channel arrays, `g_slot_migrating_to`/`g_slot_importing_from` (mirroring Redis's own `server.cluster->migrating_slots_to`/`importing_slots_from`), consulted only by the dispatch chokepoint's `ASK` check and by `CLUSTER NODES`' `[slot->-<id>]`/`[slot-<-<id>]` markers on this node's own line (`clusterGenNodeDescription`, `cluster.c:5329-5344`) — never by `cluster_owned_ranges()`, so a migration in progress cannot leak into `CLUSTER SLOTS`/`SHARDS`/`NODES`'s reported ownership or into `cluster_size`. A definitive `SETSLOT NODE` clears both side-channel arrays for that slot, so a concluded migration cannot leave a stale marker naming a migration that already finished. (An earlier version of this feature conflated the two facts — `SETSLOT MIGRATING` wrote the same `g_slot_owner` array `cluster_owned_ranges()` reads, so a client refreshing its slot map would see the slot move to the migration target before any key had actually moved, and get misses instead of `ASK`; caught in final review and fixed in the same milestone — see `test_p5_cluster_ownership.py`'s migration assertions.) `CLUSTER COUNTKEYSINSLOT`/`GETKEYSINSLOT` walk the real keyspace via `DataStore::for_each_key` (no cached slot-to-keys index, so results are exactly correct, and `for_each_key` hands out each key by reference instead of building a `std::vector` copy of the keyspace first; like Redis's slot index it counts and lists expired keys too and deletes nothing, item 37 — but see Missing below for the O(N) walk this still carries and an ordering divergence). `cluster-enabled` is a real startup-only (Redis's own `IMMUTABLE_CONFIG` treatment) config field, refused by `CONFIG SET`, and gates the entire `CLUSTER` command before any subcommand dispatch — including read-only ones like `KEYSLOT` and `HELP` — exactly where Redis's `clusterCommand()` does it; a node refuses to start with `cluster-enabled yes` if its resolved announced address is a wildcard (`0.0.0.0`, `::`, `*`, or empty), whether that resolution comes from the `bind` fallback or an explicit `cluster-announce-ip` naming a wildcard itself; `CONFIG SET cluster-announce-ip` carries the same refusal at runtime (the two port parameters beside it were already range-checked). `CLUSTER SLOTS` groups contiguous slots by their real owner and omits unassigned slots entirely, matching `clusterReplyMultiBulkSlots`; each node entry is Redis 7.2's 4-element shape (ip, port, 40-hex id, and an additional-endpoints map that is always empty because PeaDB has no `cluster-preferred-endpoint-type` config to make it anything other than the default "ip"), and that map is RESP2/RESP3-correct (`*0` vs `%0`). `CLUSTER SHARDS` returns one shard per real owner: a 2-field map (`slots`, a flat start/end array; `nodes`, an array of 7-field maps — `id`, `port`, `ip`, `endpoint`, `role`, `replication-offset`, `health`); every node reports `role:master`/`health:online` because PeaDB models no replicas inside the cluster (a deployment wanting both sharding and replica failover runs `REPLICAOF` on top of the cluster model, separately), and `replication-offset` is the same counter `INFO replication`'s `master_repl_offset` reports. `CLUSTER NODES` joins lines with `\n` (not `\r\n`, matching `clusterGenNodesDescription`), reports every node's own announced address — including self, which used to hardcode `127.0.0.1` regardless of `cluster-announce-ip` — and each node's real owned slot ranges. `CLUSTER INFO` derives `cluster_slots_assigned`/`cluster_slots_ok`/`cluster_state` from real slot coverage (`ok` only once all 16384 slots have an owner, matching Redis's `cluster-require-full-coverage yes` default — PeaDB does not expose that config, so full coverage is always required) and `cluster_size` from the count of distinct owners that hold at least one slot, not the whole known-node count. `CLUSTER MEET`'s port-parse error now uses Redis's exact wording, `"Invalid base port specified: <arg>"` (`cluster.c:5958`), instead of a made-up message; `MEET` also refuses a target that resolves to this node's own announced address, and the peer-reachability round trip (the synchronous `MEETBACK` callback, `try_send_cluster_meetback`) is now bounded by a 1-second connect/read timeout instead of the OS default — see Missing below for what this does and does not fix. `CONFIG SET cluster-announce-ip`/`-port`/`-bus-port` re-derive `g_cluster_nodes[0]` (id included, since the id is derived from the address) immediately, so `CONFIG GET`, `CLUSTER NODES`, and `CLUSTER SLOTS` can never disagree about this node's own advertised address regardless of whether the `CONFIG SET` lands before or after the first `CLUSTER` call has lazily snapshotted the node table. Full design rationale: `docs/decisions/p5-cluster-addressing-and-version-provenance.md`.
- Open defects (2026-10 review): routing looks only at the first key and there is no CROSSSLOT (item 64); no CLUSTERDOWN, no saved topology and no health reporting (item 65); standard tooling, resharding, SETSLOT checks and MEET (item 66); multi-database commands, ignored `cluster-*` settings and the bus listener (item 67); `COUNTKEYSINSLOT`/`GETKEYSINSLOT` cost about 90–100 ms per call at 1M keys, against about 0.1 ms in Redis (measured on macOS).
- Missing: no cluster bus gossip protocol at all — the bus port opened at `announced_port + 10000` is a placeholder listener that answers a bare `PONG`, not a MEET/PING/PONG/FAIL message exchange, so topology never propagates between nodes on its own; no failure detection (no `PFAIL`/`FAIL` state machine, because there is no gossip channel for nodes to disagree about liveness over); no automatic failover (there are no replicas in the cluster model at all, so there is nothing to promote); every node's config-epoch reads as a hardcoded `1` (`cluster_current_epoch`/`cluster_my_epoch` in `CLUSTER INFO`, and the config-epoch column of every node's `CLUSTER NODES` line) — Redis assigns and bumps a real, growing epoch per node so a node or client can tell whose slot claim is newer after a partition or a manual race; PeaDB has no gossip protocol for two nodes to ever disagree about slot ownership in the first place, so there is no conflict left for an epoch to resolve, and a constant says that plainly — inventing varying epoch numbers with no real conflict behind them would claim a resolution process that does not exist, which is worse than the constant; no `nodes.conf` persistence (topology is entered per node via `CLUSTER MEET`/`SETSLOT`/`ADDSLOTS(RANGE)` and is lost on restart — an operator or their orchestration tooling must re-issue it, or script it into node startup, every time a node restarts — and the natural shape of that script, a `MEET` loop from every node to every known address including its own, used to hang the process outright on the self-address case and could block it for minutes on a genuinely unreachable one, since `try_send_cluster_meetback` ran an unbounded, synchronous `connect()`/`read()` on the single event-loop thread; `MEET` now refuses a self-address target and bounds the round trip to any other target with a 1-second connect/read timeout, but the round trip is still synchronous, so a bad address still stalls every other client on this node for up to that timeout — a full fix makes the handshake asynchronous, unchanged XL-scope future work); `CLUSTER MEET`'s peer-reachability round trip (the synchronous `MEETBACK` callback) accepts numeric IPv4 only, via `inet_pton(AF_INET, ...)` — no hostname resolution and no IPv6; `CLUSTER SETSLOT MIGRATING`/`IMPORTING` do not enforce Redis's ownership preconditions (`"I'm not the owner of hash slot %u"` when `MIGRATING` a slot this node does not own, `"I'm already the owner of hash slot %u"` when `IMPORTING` a slot it already owns — `cluster.c:6091-6110`), there is no `SETSLOT STABLE` to clear a migrating/importing state other than a definitive `SETSLOT NODE`, and PeaDB does not yet special-case `ASKING` traffic for an importing slot (a slot this node is importing is simply not locally owned until the final `SETSLOT NODE`, so it still `MOVED`s rather than accepting `ASKING`-flagged commands the way Redis does). `CLUSTER COUNTKEYSINSLOT`/`GETKEYSINSLOT` are accurate but not O(1), and this is a cost claim, not just a completeness one: Redis's `countKeysInSlot` (`cluster.c`) is O(1) — a single `by_slot[hashslot].count` read — while PeaDB has no slot-to-keys index and instead walks the entire keyspace on every call via `DataStore::for_each_key`, which visits each key by reference (no `std::vector<std::string>` copy of the keyspace, no per-key string allocation); `COUNTKEYSINSLOT` only increments a counter per key it visits, and `GETKEYSINSLOT` collects and sorts only the keys that actually match the target slot, not the whole keyspace as it used to (a whole-keyspace `store().keys("*")` copy followed by a whole-keyspace `std::sort` before either subcommand had even looked at a single key's slot). Both are still O(N) in the database's key count — an admin tool that loops `COUNTKEYSINSLOT` over all 16384 slots (a plausible rebalancing-audit pattern) still triggers 16384 full keyspace walks, not 16384 O(1) reads, and on PeaDB's single-threaded event loop each walk still stalls every other client for its duration — but the constant factor per walk is now a single allocation-free pass instead of "copy every key into a vector, then (for `GETKEYSINSLOT`) sort all of them regardless of how few land in the requested slot." `GETKEYSINSLOT` also returns keys in lexicographic order (an artifact of the sort used to make results deterministic across calls), not Redis's slot-index (bucket-scan) order — a caller that relies on result order for anything beyond "some keys in this slot" will see a different first key than against real Redis. Redis 7.2.5 has 27 canonical `CLUSTER` subcommands (28 `cluster-*.json` command specs in the pinned source, minus `SLAVES`, which is a deprecated-since-5.0.0 alias for `REPLICAS`, not a distinct subcommand); PeaDB implements 15 of them, and 12 remain unimplemented: `BUMPEPOCH`, `COUNT-FAILURE-REPORTS`, `FAILOVER`, `FLUSHSLOTS`, `FORGET`, `LINKS`, `MYSHARDID`, `REPLICAS`, `REPLICATE`, `RESET`, `SAVECONFIG`, `SET-CONFIG-EPOCH`. `MEETBACK` is a PeaDB-only extension, not a real Redis subcommand at all — it lets a `MEET`ed peer learn of the meeting node immediately, synchronously, since there is no gossip round for that news to travel on otherwise — so it is not counted among the 15.
- Tracking: long-term cluster milestone (gossip protocol, failure detection, automatic failover, and `nodes.conf` persistence are all separate, XL-scope future work). The operator-configured topology model this item now closes against is a deliberate, documented design choice — see the decision record above — not a stopgap awaiting a rewrite; large regulated customers already run an external orchestrator that owns membership and placement, so a smaller, auditable, explicitly-administered topology is the intended shape here, not a shortcut. Cluster mode stays `experimental` until items 43 and 64–67 are closed or the scope decision changes.

7. AUTH / ACL enforcement
- Status: `partial` (default-user AUTH enforced; multi-user ACL engine still missing)
- Owner: security-compat
- Severity: high
- Target milestone: P3
- Implemented: real default-user authentication. `requirepass`/`masterauth` via config file,
  CLI flags, and `CONFIG GET/SET`; a dispatch-time gate returns `-NOAUTH Authentication required.`
  for unauthenticated clients (commands flagged `no_auth` — AUTH/HELLO/QUIT/RESET — are exempt);
  `AUTH` and `HELLO <proto> AUTH <user> <pass>` perform a constant-time compare and return
  `-WRONGPASS` on mismatch and the "no password is set" error when `requirepass` is empty.
  protected-mode (default on) refuses non-loopback clients when no password is set. Auth state
  follows Redis's `clientSetDefaultAuth`: a client is authenticated at connect time iff no
  password is set, so a later `CONFIG SET requirepass` never retroactively de-authenticates
  open connections, and `RESET` re-derives the flag from the current password. Hardening:
  `MODULE LOAD` is gated behind `enable-module-command` (default off, blocks the dlopen RCE
  vector); `rename-command FROM TO` (TO empty disables) lets operators neutralise dangerous
  verbs; the RESP parser matches Redis framing byte-for-byte (`proto-max-bulk-len` 512 MB bulk
  cap, `INT_MAX` multibulk cap with incremental arg reads, a 64 KB single-line desync limit, and
  a 1 GB per-client query-buffer cap close the unbounded-allocation / OOM DoS); unauthenticated
  clients get Redis's tighter pre-auth caps (>10 multibulk elements or >16 KB bulk are refused
  before buffering); the Lua sandbox now removes `os`/`io`. `ACL WHOAMI`/`USERS`/`LIST`/`CAT`/
  `GETUSER`/`GENPASS`/`HELP` truthfully introspect the single `default` user: `ACL LIST` and
  `ACL GETUSER` print its password the way Redis does, `#<sha256-hex>` of `requirepass` or
  `nopass` when none is set (`ACLDescribeUser`/`ACLUpdateDefaultUserPassword`); `ACL CAT
  <category>` filters the real generated per-command category metadata rather than a
  hand-written list; `ACL GENPASS` draws from the same entropy source as the replication run
  id. `ACL SETUSER`/`DELUSER`/`LOAD`/`SAVE`/`LOG`/`DRYRUN` refuse with an error naming this gap
  instead of the previous behavior — `SETUSER` used to answer `+OK` and silently discard its
  rule, and the others were unregistered — because there is no rule engine to create, delete,
  persist, or execute a rule against, and no log of auth events to show or reset.
- Missing: full multi-user ACL rule evaluation (users, key patterns, command categories,
  pub/sub channels), the rule-authoring subcommands themselves (`SETUSER`/`DELUSER`/`LOAD`/
  `SAVE`/`DRYRUN`), `ACL LOG`, and TLS — all deferred as dedicated XL tracks. One upstream
  `unit/slowlog` test needs a working `SETUSER` to redact its arguments and is skipfile-tracked
  (`scripts/redis/skipfiles/unit_slowlog.skip`).
- Open defects (2026-10 review): audit counters and logging (item 60); weaker defaults than Redis for DEBUG, CLIENT SETINFO and the password compare (item 61). Since the item 24 fix, a config with `user` or `aclfile` lines, or one that turns TLS on, stops startup, so a redis.conf that sets its password that way no longer starts PeaDB with no password.
- Tracking: security hardening milestone.

8. REPLICAOF in-process streaming
- Status: `partial` (functional + auto-reconnect; no automatic failover)
- Owner: replication-compat
- Severity: medium
- Target milestone: P3-reconnect
- Implemented: In-process TCP client (`replica_do_fullsync`). Does PING → (AUTH masterauth if set) → REPLCONF → PSYNC ? -1 → RDB load → continuous command stream. **Automatic reconnect**: a generation-tagged supervisor reconnects with exponential backoff (0.5→30 s) on link loss, sets `master_link_status:down` while disconnected, and stops promptly on a newer REPLICAOF (incl. NO ONE). **Replica expiry correctness**: replicas no longer actively self-expire — the master propagates a DEL for each actively-expired key, so clocks can't diverge. **min-replicas-to-write** counts only online replicas whose last ACK is at most `min-replicas-max-lag` whole seconds old, using the same predicate as INFO's `min_slaves_good_slaves`. Both settings apply at startup and through CONFIG SET (including `min-slaves-*` aliases); either zero disables admission. A replica and the master stream/AOF replay bypass this master-only check. 12. Key eviction (maxmemory-policy)
- Status: `partial` — the policies, the memory they act on (item 38) and the OOM rules (item 39) are Redis's since 2026-10-07; the choice of victim is sampled without Redis's eviction pool, and LFU counters never decay.
- Owner: memory-eviction
- Severity: medium
- Target milestone: P4
- Implemented: all eight `maxmemory-policy` modes — `noeviction`, `allkeys-lru`/`-lfu`/`-random`, `volatile-lru`/`-lfu`/`-random`/`-ttl` — through `perform_evictions()` in `src/command.cpp`, a port of Redis's `performEvictions()`: it runs before each command a client sends while `maxmemory` is set (not the commands EXEC or a script runs), computes the bytes to free once, from `used_memory` less the memory not counted (item 38), and evicts victims picked by `DataStore::evict_one()` until the memory freed by the deletes themselves reaches it. After every 16 keys it stops once it has run for `maxmemory-eviction-tenacity`'s time limit (10, the default: 500 us; 100: no limit; applied since 2026-10-07, from the config file and `CONFIG SET`), and the eviction timer (Redis's `startEvictionTimeProc()`, `run_eviction_cycle()` on each event-loop pass, which then does not sleep) goes on until memory is within the limit, so a large eviction never stops the server for long; `CONFIG SET maxmemory` starts the timer too and logs Redis's warning when the new limit is below the used memory. - Status: open defect. Evidence: reproduced 2026-10-09 against the pinned Redis 7.2.5 (found by the review of the item 19 fix).
- Owner: persistence-compat
- Severity: medium
- Target milestone: R8
- Implemented: a renamed command (`rename-command`) runs under its new name.
